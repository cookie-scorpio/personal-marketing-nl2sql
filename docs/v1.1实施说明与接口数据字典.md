# 个金营销 NL2SQL 平台 v1.1 实施说明与接口数据字典

本文记录 v1.1 的实际实现、数据库结构、API、配置和验证结果。v1.0 文档保留为历史版本；当前接口契约见 contracts/openapi/crm-nl2sql-mvp-v1.yaml，文件名保留，版本号已更新为 1.1.0。

## 1. 版本范围

平台面向个人金融营销模拟数据，支持用自然语言查询客户、交易、产品持有和营销活动，并理解结果。本次只扩展查询控制、自由 SQL 修复与降级、数据展示，以及相关口径判断，不扩展其他业务模块。

技术栈保持 JDK 17、Spring Boot 4.1.1、MyBatis-Plus 3.5.16、Maven 3.9.16、Vue 3、TypeScript、Element Plus 2.x、ECharts 6、MySQL 8.4、Redis 7.x。查询统一使用 MySQL，不使用 Spark SQL 或 Hive。Milvus 和 BCG-E3 继续保留接口与配置，不在本版实际连接；Redis Cluster 保留配置示例，不改动现有部署。

### 1.1 本版已实现

- 本人未结束的任务可取消，包括等待、识别、反问、确认、SQL执行、修复、降级和整理结果阶段。
- 单次 MySQL 执行默认超时 60 秒，可配置；超时与主动取消均停止后续 SQL、修复和降级。
- 模型 SQL 发生可修复的数据库表达错误后，最多调用模型修复两次；修复次数持久化，不因风险确认而重置。
- 修复不可用或次数用尽时，尝试能完整覆盖原问题的固定模板；无合适模板则返回原因和调整建议，不返回替代口径或虚构数据。
- 每条修复或降级 SQL 重新经过只读、对象白名单、数据范围和风险检查；新 SQL 需要风险确认时生成新令牌。
- 结果列增加角色、单位、聚合方式和权重字段描述，支持柱状图、折线图、面积图、构成图、散点图和热力图。
- 同一结果可显示多张图，覆盖所有可绘制的指标。人数与金额分图展示，不压在一个纵轴上。
- 均值和比率不直接相加；已知分母时计算加权均值，未知分母时明确标注为返回分组均值。
- 客户时间口径不明确时先确认，禁止擅自把“近90天客户”理解成“近90天开户客户”。
- 延续登录、JWT、三种角色数据范围、规则优先、模型自由查询、澄清、确认、查询历史和审计。

### 1.2 年龄段问题的修复依据

在原查询历史中，“分析近90天各年龄段客户数量和平均资产”对应的 SQL 已返回 customer_count 和 avg_asset_amount，但将时间条件自行落在 open_date 上。旧 ResultAssembler 只选一个主要数值列，前端也只渲染 charts[0]，导致平均资产未展示。

v1.1 分别处理两个问题：

1. 先询问时间约束的是哪种业务时间。用户明确开户时间后才按开户日期筛选；明确交易时间时交给模型处理交易口径，不能重复累计同一客户的资产。
2. 查询结果中的客户数量与平均资产都进入展示，分别标明人和元/万元。平均资产指所选客户当前资产的客户均值，不代表过去90天的资产时间均值。

### 1.3 前端设计约定

主任务仍是“提出业务问题并理解结果”。沿用近白背景、细边框、中行红强调色、系统中文无衬线字体、Element Plus 图标；使用 4/8/12/16/24/32 像素间距和现有圆角。主要操作为发送查询、补充后继续或确认并执行，取消为明确的次级操作。

结果按“状态说明—指标及口径—全部图表—分析—明细/SQL依据”组织。取消采用中性提示，超时明确说明已终止，降级使用琥珀色说明原因；不把无数据的降级显示成正常查询成功。图表支持尺寸变化、空值、长标签、较多分组和减少动态效果设置。桌面仍为主要使用环境。

### 2.2 查询控制配置

| 配置 | 环境变量 | 默认值 | 含义 |
|---|---|---|---|
| app.query.execution-timeout-seconds | QUERY_EXECUTION_TIMEOUT_SECONDS | 60 | 单次SQL执行时限，正整数秒 |
| app.query.max-result-rows | QUERY_MAX_RESULT_ROWS | 100 | 结果行数上限，同时设置到JDBC Statement |
| app.query.max-clarification-rounds | QUERY_MAX_CLARIFICATION_ROUNDS | 2 | 反问轮数上限 |
| app.model.deepseek.read-timeout-seconds | DEEPSEEK_READ_TIMEOUT_SECONDS | 60 | 单次模型HTTP响应读取超时 |
| app.model.deepseek.max-tokens | DEEPSEEK_MAX_TOKENS | 4096 | 模型首次输出上限 |
| app.model.deepseek.retry-max-tokens | DEEPSEEK_RETRY_MAX_TOKENS | 8192 | 首次规划发生空回复/截断时的重试输出上限 |
| app.model.deepseek.thinking-enabled | DEEPSEEK_THINKING_ENABLED | false | 结构化规划默认关闭思考模式 |

SQL 的 60 秒不含队列、模型调用、连接池等待、风险确认和人工澄清时间，也不是整项任务总时限。每次修复后的 SQL、模板 SQL 都分别受同一个执行时限约束。

SQL 修复上限在代码中固定为 2，不提供放宽上限的配置。初次规划沿用 v1.0 的一次空回复/截断重试；每次 SQL 修复只发一次 HTTP 请求，不再嵌套响应重试。因而正常初次规划加两次修复最多3次请求；初次规划自身发生一次响应重试时，最多4次请求。取消后不会继续下一次响应重试。

### 2.3 升级与部署

1. 备份数据库，停止旧版本任务入口并等待或处理运行中任务，再停止旧后端。
2. 部署 1.1.0 后端，Flyway 应用 V4，仅为 query_task 增加4个字段。
3. 部署同版本前端 dist，继续代理 /api 和 /actuator/health。
4. 检查健康接口、普通查询、时间澄清和取消接口。
5. 多实例必须统一升级。旧版本写入不带 state_version，不能与新版共同处理同一任务。

新增状态和结果字段需要前后端同步升级；HTTP 路径仍为 /api/v1，不表示客户端可忽略新增终态。历史数据不自动重新生成图表，复用历史问题会创建新查询。

数据库迁移不能通过删除已应用的 V4 文件回退；回退前需评估新结果 JSON 和终态与旧应用的兼容性，保留备份。Windows 下如旧 JAR 被占用，先停止对应旧进程再替换。

## 3. 处理流程与关键实现

~~~text
问题 → 客户时间口径确认 → 规则或模型计划 → 完备性与安全检查 → 风险确认 → MySQL
                                                                      ├─ 成功 → 多指标、多图 → SUCCESS
                                                                      ├─ 取消 → CANCELLED
                                                                      ├─ 超时 → TIMED_OUT
                                                                      └─ 可修复SQL错误
                                                                          → 修复（最多2次）
                                                                          → 重新校验/必要时重新确认
                                                                          → 仍失败 → 固定模板/说明 → DEGRADED
~~~

### 3.1 取消与并发状态

TaskStateStore 使用 state_version 条件更新。后台阶段推进、澄清和确认必须成功消费当前版本；取消使用只更新控制字段的原子语句并递增版本。后台持有的旧对象不能把已取消任务覆盖为成功。相同任务的异步执行入口也用版本更新认领，重复确认不会并行执行同一计划。

MySqlQueryExecutionGateway 保存正在执行的 PreparedStatement，设置 setQueryTimeout 与 setMaxRows，并通过 Statement.cancel 中止执行。执行实例每约200毫秒检查任务持久状态，因而即使取消请求落在另一个实例，也能发现取消。执行结束后先停止取消回调，再交回连接池，防止迟到的取消影响下一次复用。

取消接口返回 CANCELLED 表示任务已停止推进，数据库中断可能存在短暂传播时间，不承诺零毫秒停止。正在进行的模型 HTTP 请求不保证立即断开；其结果会被丢弃，后续调用和 SQL 不再执行。进程崩溃后的任务自动恢复不在本版范围。

JDBC行为参考：[Java 17 Statement](https://docs.oracle.com/en/java/javase/17/docs/api/java.sql/java/sql/Statement.html)。

### 3.2 修复与降级边界

只有来自模型 SQL 的已知表达错误进入修复：1054（字段/别名）、1064（语法）、1055/1140（分组）、1111（聚合位置）、1241/1242（标量表达式）、1305（函数）。只发送错误分类、失败 SQL、原问题和授权数据字典，不发送数据库原始错误正文或结果明细。

连接失败、数据库权限错误、取消和超时不修复。初始 SQL 安全校验未通过时直接失败。修复响应不可用、没有 SQL、要求重新解释，或修复 SQL 未通过校验时可以提前停止修复并尝试受控模板，因此“最多两次”不表示每次都必须用满两次。

修复次数在发出调用前持久化。新修复计划如触发风险，会停在 CONFIRMING；确认后执行保存的修复 SQL，不重新生成，也不重置修复次数。

| 降级模板 | 覆盖范围 |
|---|---|
| RULE_加原意图名 | v1.0规则支持、全部条件可被解析的原问题 |
| CUSTOMER_AGE_ASSETS | 按年龄段统计客户数量与当前平均资产；支持已明确的开户时间或明确不限定时间 |
| CUSTOMER_GENDER_ASSETS | 按性别统计客户数量与当前平均资产；时间要求同上 |

模板只接受完整匹配的表达。未知地区、额外筛选、同比、复杂分组或交易筛选要求不能静默删除。模板仍绑定当前用户范围。没有匹配模板时 result.rows、charts 和业务指标为空，fallback.data_available=false，返回原因与建议。

### 3.3 数据展示规则

| 数据形态 | 展示 |
|---|---|
| 单个结果/单项指标 | 指标卡和明细，不强行画图 |
| 一个分类维度和多个指标 | 每个指标独立柱状图；类别较多或标签较长时横向展示 |
| 时间维度 | 按时间排序的折线图；明确建议AREA且数值非负时用面积图 |
| 少量类别的非负可加总指标 | 柱状图；类别构成适合时另给构成图 |
| 无分类维度的两个数值，或合法散点建议 | 散点图 |
| 两个分类维度与指标 | 每个有效指标一张热力图，前提是维度组合唯一 |
| 重复维度、超过两个分类维度等无法直接解释的形态 | 保留指标/分析/明细，不擅自合并或重复计算 |
| 明确TABLE计划 | 保留明细和指标，不生成图表 |

模型可在 columns 中描述字段角色与单位。后端根据实际列名、实际数据类型和语义规则校正建议；旧模型响应没有 columns 时仍可推断常见字段。不直接使用模型提供的完整 ECharts 配置。

空值保留为空，不补零；从全部返回行中寻找非空值识别类型，避免首行为空就漏掉指标。数字编号、年龄段编码不当作指标。构成图不会用于负数、全零、均值或比率。图表无论一张还是多张，都只消费已有结果，不额外查询或调用模型。

已知平均资产与 customer_count 对应时，按人数加权；转化率与 contact_count 对应时，按触达人数加权。未知分母的均值明确标注“返回分组均值（非总体均值）”。权重缺失、负数或全零时不编造加权均值。所有统计仅基于当前返回的有限结果，不宣称是全库汇总、跨组去重人数或经营因果结论。

### 4.12 数据关系与迁移

业务关联通过编号建立：交易、产品持有、营销触达均关联客户；营销触达关联活动；客户关联经理。当前未使用物理外键，模拟数据生成器负责保持关联一致。

迁移顺序：V1创建11张业务/平台表，V2初始化术语，V3扩展查询任务来源、置信度、展示类型和风险信息，V4增加状态版本、修复次数、字段语义和降级记录。Flyway自身还会维护`flyway_schema_history`技术表，不属于业务模型。


V4只修改query_task，不增加业务表或历史资产数据。新增终态仍存入原status_code列；result_json保存扩充后的QueryResult。其他表及索引沿用v1.0。

## 5. API 设计与数据字典

所有业务接口使用 JWT Bearer 认证，字段为 snake_case，沿用统一响应：

~~~json
{"code":0,"message":"处理成功","request_id":"请求追踪编号","data":{}}
~~~

### 5.1 接口总览

| 方法与路径 | 输入 | 返回data |
|---|---|---|
| POST /api/v1/auth/login | username、password | access_token、token_type、expires_in、user |
| GET /api/v1/auth/me | 无 | 当前用户与角色数据范围 |
| POST /api/v1/queries | session_id、query_text，可选preferred_display | task_id、session_id、status、progress、status_url |
| GET /api/v1/queries/{taskId}/status | 路径taskId | TaskStatus |
| POST /api/v1/conversations/{sessionId}/messages | task_id、question_id、answer_text或selected_options | 重新处理的任务信息 |
| POST /api/v1/queries/{taskId}/confirmations | confirm_token、decision，可选reason | TaskStatus |
| POST /api/v1/queries/{taskId}/cancel | 无请求体 | TaskStatus，本版新增 |
| GET /api/v1/query-history | page_no、page_size、keyword | items、total、page_no、page_size |
| DELETE /api/v1/query-history/{historyId} | 无 | history_id、deleted |
| GET /actuator/health | 无，无需登录 | 健康状态 |

登录、历史与删除的请求口径延续 v1.0。page_no 从1开始，page_size 为1–100；删除只影响可见历史。user 包含 user_id、username、display_name、role、region_code，以及可选 branch_id、manager_id。

### 5.2 提交、澄清与确认

提交示例：

~~~json
{"session_id":"11111111-1111-4111-8111-111111111111","query_text":"分析近90天各年龄段客户数量和平均资产","preferred_display":"AUTO"}
~~~

query_text 为1–1000字。preferred_display 为兼容字段，实际展示仍由服务端计划及数据形态决定，不能借此传入SQL。

时间口径不明确时返回 ASKING：

~~~json
{
  "task_id":"22222222-2222-4222-8222-222222222222",
  "session_id":"11111111-1111-4111-8111-111111111111",
  "status":"ASKING","progress":30,
  "message":"这里的时间范围要按什么业务时间筛选客户？客户资产只有当前快照，不能计算期间资产的时间平均值。",
  "intent":"CUSTOMER_FILTER","clarification_round":0,
  "repair_attempts":0,"execution_timeout_seconds":60,"cancellable":true,
  "question":{
    "question_id":"33333333-3333-4333-8333-333333333333",
    "type":"TIME_BASIS",
    "prompt":"这里的时间范围要按什么业务时间筛选客户？客户资产只有当前快照，不能计算期间资产的时间平均值。",
    "options":["按开户时间筛选，统计这些客户的当前资产","按交易时间筛选有交易的客户，统计其当前资产","不限定时间，统计当前客户与当前资产"],
    "recognized_slots":{"时间范围":"2026-05-29 至 2026-08-27"}
  }
}
~~~

前端不自动预选时间口径。补充请求：

~~~json
{"task_id":"22222222-2222-4222-8222-222222222222","question_id":"33333333-3333-4333-8333-333333333333","answer_text":"按开户时间筛选，统计这些客户的当前资产"}
~~~

服务端将回答作为“时间口径：”追加到合并问题中，继续处理。普通信息补充和矛盾澄清仍使用原有机制；补充不会重置修复次数。

风险确认请求：

~~~json
{"confirm_token":"服务端本次返回的令牌","decision":"CONFIRM"}
~~~

decision 为 CONFIRM 或 REJECT。REJECT 走统一取消逻辑；确认只消费当前令牌和当前状态。修复后出现新风险时，旧令牌不能确认新 SQL。

### 5.3 取消接口

POST /api/v1/queries/{taskId}/cancel 无请求体，只能操作当前用户自己的任务。成功取消、重复取消、任务已结束均返回200和实际状态。

~~~json
{
  "code":0,"message":"处理成功","request_id":"req-cancel",
  "data":{
    "task_id":"22222222-2222-4222-8222-222222222222",
    "session_id":"11111111-1111-4111-8111-111111111111",
    "status":"CANCELLED","progress":100,
    "message":"查询已取消，不会继续修复或降级执行",
    "clarification_round":0,"repair_attempts":0,
    "execution_timeout_seconds":60,"cancellable":false
  }
}
~~~

取消与正常完成竞争时，先成功提交的终态生效；如果正常完成已经提交，取消返回 SUCCESS，而不是把已完成结果改成取消。不存在或不属于当前用户的任务统一返回404001，避免泄漏他人的任务信息。

### 5.4 TaskStatus 字段

| 字段 | 类型 | 说明 |
|---|---|---|
| task_id、session_id | string | 任务及会话编号 |
| status | string | 当前阶段或终态，见下表 |
| progress | integer | 阶段进度0–100，不是SQL物理执行百分比；修复时可能回退 |

| clarification_round | integer | 已完成反问轮数 |
| repair_attempts | integer | 本任务已消耗修复调用次数，0–2，新增 |
| execution_timeout_seconds | integer | 单次SQL执行超时配置，新增 |
| cancellable | boolean | 当前是否允许取消，新增 |
| question | object，可缺省 | 反问编号、类型、问题、选项和已识别条件 |
| confirmation | object，可缺省 | confirm_token、risk_level、message、reasons |
| result | QueryResult，可缺省 | SUCCESS或DEGRADED时的结果 |
| error | object，可缺省 | 面向用户的message，不包含数据库堆栈 |

| 状态 | 是否终态 | 说明 |
|---|---|---|
| RECEIVED | 否 | 已接收/重新进入处理 |

| SQL_GENERATING、VALIDATING | 否 | 生成与校验计划 |

无匹配模板时 data_available=false，rows=[]，charts=[]，metrics=[]，sql_preview=""；即使原失败SQL仍保留在query_task中，也不会展示为已成功执行的结果依据。

### 5.6 错误码与审计

沿用 v1.0 的400001–400003（参数）、401001（认证）、403102–403104（对象/范围）、404001（归属或不存在）、409001–409003（澄清/确认状态）、422101–422103（SQL）、502101–502107（模型响应）、503101–503102（模型不可用）、500000（其他错误）。

新增409004：任务状态已变更，当前澄清或确认提交未生效，请刷新后重试。SQL超时通过任务 TIMED_OUT 和 error.message 表达，不把异步任务超时伪装成提交接口的 HTTP 超时。

新增或复用审计事件：QUERY_SQL_ERROR、QUERY_REPAIR_STARTED、QUERY_FALLBACK、QUERY_CANCELLED、QUERY_TIMED_OUT、QUERY_DEGRADED，以及原有接收、反问、确认、成功和失败。取消与终态历史以成功提交状态的一方记录；附属记录失败会记录服务日志，不把已提交终态改写为失败。尚未增加审计写入失败的可靠重试机制。

## 6. 本版未实现

不新增 Milvus/RAG 实际连接、动态元数据管理、术语管理页面、完整SQL AST权限校验、EXPLAIN成本预测、跨任务上下文、SSE、导出收藏、Redis Cluster部署、生产统一认证或独立营销业务页面。

不新增历史资产序列、同比环比、经营归因、异常检测模型；不能因增加图表就把数据库不支持的指标解释成已实现。提交级幂等键、任务崩溃恢复、确认令牌独立到期时间、分布式执行队列仍未实现；本版只补上取消与确认等必要的状态竞争保护。

SQL校验延续v1.0基础静态规则，并非生产级完整语法与权限证明。使用真实客户数据前仍需要专门的只读账号、完整行列权限、AST验证、敏感信息控制和审计建设。

### 7.2 复验命令

在 crm/backend 中执行：

~~~powershell
# 默认测试：不访问MySQL的测试运行，4项真实数据库用例跳过
~~~

### 7.3 注意事项

- 修复次数是调用预算，网络失败或不可用响应也可能消耗已记录的一次额度。
- 取消与超时不触发模板；用户需要自行调整条件、重新提交才能开始新任务。
- 模型在修复阶段必须保留原业务含义，后端继续执行既有安全检查；复杂语义是否等价仍不等同于形式化证明。
- 结果行数有限，图表和分析必须结合查询条件及SQL理解，不能把有限分组当作全库统计。
- 不把客户数据、数据库密码、API密钥、真实SQL报错正文写入提交内容。
- v1.0文档和既有迁移文件保留，不根据新实现反向改写历史验收记录。
