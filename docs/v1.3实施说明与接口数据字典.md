# 个金营销 NL2SQL 平台 v1.3 实施说明与接口数据字典

本文按 v1.0 文档的“版本范围—运行配置—处理流程—数据库—API—未实现项—验收—许可”结构记录 v1.3 的实际实现。v1.0、v1.1、v1.2 文档保留历史记录；升级、接口调用和当前能力以本文及代码为准。所有姓名、手机号占位值、资产和交易均为虚构演示数据。

## 1. 版本范围

平台面向个人金融营销查询：业务人员用自然语言描述问题，系统确认查询对象和统计条件，生成受控 MySQL SQL，返回指标、图表、明细及简要分析。

技术栈保持 JDK 17、Spring Boot 4.1.1、MyBatis-Plus 3.5.16、Maven 3.9.16、Vue 3、TypeScript、Element Plus 2.x、ECharts 6、MySQL 8.4、Redis 7.x。SQL AST 使用现有依赖带入的 JSqlParser 5.2。当前只使用单节点 Redis，不建设 Redis Cluster。Milvus、BCG-E3 仍只保留外置接口，不连接向量服务。后续查询统一使用 MySQL，不使用 Spark SQL 或 Hive。

### 1.1 本版已实现

| 本版需求 | 实现与边界 |
|---|---|
| 身份补充明确类型 | 先选择客户编号、客户虚拟姓名或手机号后四位，再显示对应输入框；服务端按类型校验；候选选择仍只允许本轮已授权客户 |
| 动态统计与饼图 | 自由统计由模型理解并生成SQL，不写死金额上下界、档宽或人数；显式PIE支持超过8类，按结果人数计算构成；范围、分子、分母均受当前账户权限约束 |
| 具体SQL错误 | 403104指出未受限的表、别名、数据源序号、当前角色所需限制和改写建议；不要求业务用户补填权限 |
| SQL规划工具 | DeepSeek真实function calling，可调用get_query_schema和validate_sql，接收结构化失败原因并改写；最终业务SQL仍由原执行器校验、确认、执行 |
| 运行文件日志 | application.log、conversation.log、sql-review.log记录时间、请求/任务关联、用户输入、助手阶段、SQL、工具结果、执行结果和失败原因 |
| 会话删除 | 左侧每条会话右端删除按钮，确认后逻辑删除；活动查询须先完成或取消；审计与原消息保留，用户端所有读取入口失效 |
| 用户消息导航 | 会话左边短线目录，鼠标/键盘聚焦展开并预览输入，点击定位用户消息；可分页读取旧消息目录和正文 |
| 虚构完整姓名 | 数据库保留完整模拟姓名；V7改善已有模拟名字，生成器使用固定种子无放回选名，1万客户不重名；编号、关联和资产不因改名改变 |
| 旧版回答兼容 | V8从v1.0/v1.1任务保存的结果恢复缺失助手消息，不重跑SQL；缺少完整结果时明确提示，兼容旧结果字段 |
| 稳定排序与账号隔离 | 本人会话按创建时间倒序，相同时间用session_id倒序；打开、续问、评价和切换账号不置顶旧会话；丢弃旧账号迟到响应 |
| 消息操作 | 用户消息显示发送时间、复制、编辑后重新发送；助手消息显示复制、互斥点赞/点踩、回复时间；评价持久化且仅本人可操作 |
| 饼图尺寸适配 | 容器变化时重绘；窄屏或分类较多时收起外侧标签，完整分类、数值和占比在可换行图例保留 |
| 自动测试集 | 规则HTTP测试、真实模型评测、独立标准答案、金额边界数据、三级权限用例、JSON/CSV报告；分别计算行为、结果、展示和SQL执行情况 |

继承登录/JWT、三级数据范围、缺失与矛盾澄清、连续追问、思考开关、持久化消息/SSE、幂等与并发保护、SQL取消/超时、最多两次执行错误修复、受控模板降级、图表与分析等已有能力。没有将其他未实现项纳入本版。

### 1.2 设计取舍与客户澄清建议

核心顺序为“确定对象—核对适用条件—形成查询计划”。规则快速路径也必须经过身份校验，不能只要出现资产、交易等关键词就忽略人名或额外条件。思考开关只影响模型调用方式，不替代身份确认、权限和 SQL 校验，也不保证 SQL 一定正确。

以“帮我查找一下李先生的资产信息”为例：

1. 将“李先生”识别为不完整客户称谓，在当前用户授权范围内查询候选，不查询资产。
2. 没有候选时仅提示“当前可查询范围内未找到”，不透露权限外是否存在该客户。
3. 超过 10 名候选时不返回截断列表让用户误选，返回 input_types；用户先选择 CUSTOMER_ID、CUSTOMER_NAME 或 MOBILE_SUFFIX，再输入值。类型缺失/格式错误不推进任务。手机号后四位保留前导零，并结合原有姓名线索定位，不进行全库手机号扫描。
4. 1–10 名候选时展示编号、脱敏姓名、机构和脱敏手机，要求明确选择；完整姓名唯一匹配也不直接自动执行。
5. 选择编号后重新验证候选关系和权限，将 `customer_id` 保存到任务。生成、修复、确认恢复的每条业务 SQL 都必须保留该客户约束。
6. 当前资产/当前持有属于快照查询，不因为缺少时间机械反问。交易发生时间、开户时间、历史资产等仍按问题逐项澄清；数据库不具备的历史能力不能编造。

避免同类问题的具体措施：

| 风险 | 当前处理 |
|---|---|
| 将称谓当作完整姓名 | 先做客户定位；未确认时阻止后续业务 SQL |
| 同名客户选错 | 展示脱敏候选并由用户选择，服务端验证选择合法性 |
| 身份补充后丢失原问题 | 定位补充与原业务问题分别处理；确认后替换称谓，保留业务主题 |
| 追问误用上一个客户 | 只有追问且没有显式新身份才继承；显式编号/姓名重新定位 |
| 模型删掉客户或权限条件 | AST 分别证明账号范围和已选客户限制，修复 SQL 也必须验证 |
| 失败/取消覆盖上下文 | 只在 SUCCESS 或确有数据可用的模板降级后更新；正常空结果仍属于完成的查询 |
| 模板擅自放宽条件 | 个人资产/持有模板只完整匹配少量明确表达；额外条件进入模型；已定位单客不使用通用群体降级模板 |

姓名识别采用当前演示数据适用的中文姓名/称谓规则，并非通用实体识别模型。复杂称谓、多个人同时比较、企业名称、别名关系不保证自动解决，需提供客户编号或重新完整描述。本版没有将每个时间、指标、筛选条件都规范化成独立结构化槽位；复杂追问由带明确前后关系的文本交给模型理解，仍可能需要反问。

### 1.3 前端设计约定

使用 frontend-design 技能，具体约定见 [v1.3界面设计约定](development/v1.3界面设计约定.md)。沿用近白底、细边框、中行红主操作色、Element Plus 图标及系统中文字体。连续消息为主体，底部固定输入区，顶部提供完整会话和新建会话入口。

Enter 发送，Shift+Enter 换行；输入法组合输入不提交。运行中的思考开关不可修改。网络导致提交结果不确定时，保留原幂等键与原问题重试；明确被服务端拒绝则将问题放回输入框。新建/切换会话会断开当前进度订阅，但不会自动取消后台任务；可从会话历史返回继续处理。新会话不继承旧上下文。

左侧侧栏统一提供“新建会话”和“会话历史”，按创建时间倒序，并分为今天、昨天和更早，支持分页加载、刷新、错误重试和当前会话标记。长标题省略显示并提供完整提示；列表独立滚动。窄屏通过菜单打开，选中会话后收起。主区域不再提供历史抽屉或“查询记录”页签，旧查询历史API仅保留兼容，不再由当前页面调用。

示例问题采用等宽两列按钮，560px以下为单列；文字按按钮实际宽度自然换行。新建尚未发送问题的会话只重置前端状态，不写入数据库、不增加历史条目。加载会话、提交未确认或取消请求进行中时禁止切换，避免操作相互覆盖。

空数据库首次启动没有会话历史；已有数据库重启后仍保留用户会话。V5会回填旧任务，因此开发测试记录也可能出现在列表中。启动时不会自动清空数据，维护清理必须先确认范围并备份，不能根据标题或用户编号批量误删。v1.3新增的删除操作只隐藏用户可见入口，不自动清库。

新增交互：每条侧栏会话右端显示删除图标，点选不会触发会话切换；确认框说明审计仍保留。运行中、等待补充/确认的会话须先取消或完成，删除失败保留原列表，删除当前会话后回到新建状态。消息左侧导航条支持鼠标悬停与键盘聚焦预览、点击跳转；旧目录按100条分页，正文按原接口补页，不执行新的业务SQL。窄屏保留细导航条并限制预览宽度，尊重减少动态效果设置。目录失败显示重试入口，当前已加载消息仍可跳转。

### 2.2 模型、思考与查询配置

自由问题需配置 `MODEL_PROVIDER=deepseek`、`DEEPSEEK_BASE_URL`、`DEEPSEEK_API_KEY`、`DEEPSEEK_MODEL`。默认模型标识沿用 `deepseek-v4-flash`，地址可为服务根地址或完整 `/chat/completions` 地址。密钥只在后端配置，不传给前端或写入日志。

| 配置 | 环境变量 | 默认值 | 说明 |
|---|---|---|---|
| app.security.allowed-origins | APP_SECURITY_ALLOWED_ORIGINS | localhost:5173与127.0.0.1:5173的http来源 | 逗号分隔；独立5174测试前端需显式配置，仅允许指定来源 |
| app.model.deepseek.tools-enabled | DEEPSEEK_TOOLS_ENABLED | true | 是否开放本节3.6的受控规划工具；false回到单次JSON规划模式 |
| app.model.deepseek.max-tool-rounds | DEEPSEEK_MAX_TOOL_ROUNDS | 3 | 工具续轮上限，另有最多4个/轮及8个/次规划工具调用限制 |
| app.model.request-budget-file | MODEL_REQUEST_BUDGET_FILE | 空 | 选配跨进程HTTP尝试计数文件；评测必须设置，重启不重置 |
| app.model.request-budget | MODEL_REQUEST_BUDGET | 50 | 配置计数文件时的总尝试上限；失败、重试、工具续轮都计数 |
| app.model.provider | MODEL_PROVIDER | mock | mock 只支持规则能力，超范围明确报错 |
| app.model.deepseek.thinking-enabled | DEEPSEEK_THINKING_ENABLED | true | 适配器缺省设置；对话 API 省略 thinking_enabled 时固定按 true 接收 |
| app.model.deepseek.max-tokens | DEEPSEEK_MAX_TOKENS | 16384 | 首次最终 JSON 与思考输出的总额度 |
| app.model.deepseek.retry-max-tokens | DEEPSEEK_RETRY_MAX_TOKENS | 32768 | 空内容或截断时仅一次响应重试的额度 |
| app.model.deepseek.read-timeout-seconds | DEEPSEEK_READ_TIMEOUT_SECONDS | 120 | 模型读取超时，与 SQL 执行超时分开 |
| app.query.execution-timeout-seconds | QUERY_EXECUTION_TIMEOUT_SECONDS | 60 | 单次 SQL 的 JDBC 超时 |
| app.query.max-result-rows | QUERY_MAX_RESULT_ROWS | 100 | SQL 外层 LIMIT 允许值与返回上限；生成器默认仍用不超过100 |
| app.query.max-clarification-rounds | QUERY_MAX_CLARIFICATION_ROUNDS | 5 | 同一任务可完成的澄清轮数 |
| app.query.sql-log-dir | SQL_REVIEW_LOG_DIR | logs | 相对于后端进程工作目录，建议部署时用绝对路径 |

已有 `application-local.yml` 若显式写了 v1.1 的 `thinking-enabled: false`、4096/8192 token 或 60 秒模型超时，旧值仍覆盖默认配置。请按需要更新这些非敏感项；页面选择会覆盖该次任务的思考开关，但不改变 token 和超时配置。

模式启用通过模型接口 `thinking.type=enabled/disabled` 显式传递。思考正文不会进入 SQL 候选、消息、SSE 或日志；工具续轮所需reasoning_content仅在本次调用内存中原样回传给模型，不持久化；最终业务规划只读取最终JSON。原始模型调用未改成 token 流式 API，SSE 流式传送的是平台真实执行阶段。规则路径无模型调用，开启开关也不会强制调用模型。

协议参考：[DeepSeek Chat Completions](https://api-docs.deepseek.com/api/create-chat-completion/)、[Thinking Mode](https://api-docs.deepseek.com/guides/thinking_mode/)。本版同时提供协议替身测试与小样本真实模型评测，二者结果分别记录于第7节，不能互相替代。

### 2.3 Redis、持久化和部署

会话、消息、上下文、任务、事件均以 MySQL 为准。Redis 只缓存提交键到任务编号的映射，缓存 TTL 为24小时；Redis 不可用时仍由 MySQL 去重，不使用仅进程内锁作为跨实例保护。历史 `SessionContextStore` 不再承担新会话的上下文存储。

本版只配置 Redis 7.x 单节点。幂等缓存键形如 `nl2sql:submit:{用户编号}:SHA256(提交键)`，TTL为24小时，不引入集群运维。历史Cluster示例文件不属于本版部署要求。

部署时执行 `mvn package` 生成 `crm/backend/target/nl2sql-crm-backend-1.3.0.jar`，前端 `npm run build` 生成 `dist/`。静态服务器将 `/api`、`/actuator/health` 代理至后端。SSE 代理应关闭响应缓冲/缓存，读取超时大于55秒，例如 Nginx：

```nginx
location /api/ {
    proxy_pass http://backend:8080;
    proxy_http_version 1.1;
    proxy_buffering off;
    proxy_cache off;
    proxy_read_timeout 75s;
}
```

为 SQL 日志目录提供写入权限和持久卷；多个实例应分别写文件，再由日志收集工具汇总，不能共享同一个滚动文件。V6增加逻辑删除字段，V7重新生成虚构姓名，V8恢复旧回复并增加评价字段，升级前备份模拟库；回退应用前需评估协议与字段兼容性，不能直接删除迁移记录。

### 2.4 提示词与运行日志

三类日志共用 `SQL_REVIEW_LOG_DIR` 指定目录（沿用环境变量名，默认 `logs`），均为UTF-8、毫秒时间戳和本机时区。每一类独立按20MB/天滚动、压缩、保留14天、总量上限1GB；三类合计上限约3GB，清理由滚动策略触发。

| 文件 | 记录内容 | 不记录的内容 |
|---|---|---|
| application.log | 启停、调用耗时、结束类型、token数量元数据、异常类型与栈位置、requestId/taskId | 模型原始响应、密钥、思考正文 |
| conversation.log | USER输入、ASSISTANT阶段说明/澄清原文/结果概况与分析、session_id/task_id/user_id/status/state_version、failure_reason | 不复制完整结果表及模型思考 |
| sql-review.log | 生成/拒绝/执行SQL、绑定参数、SQL执行失败、TOOL_RESULT静态检查结果 | get_query_schema的完整内容、思考正文 |

conversation.log在事务提交后输出，避免记录已回滚的状态；日志写入本身不是数据库事务的一部分。其content/failure_reason对长数字证件/手机号、Bearer、常见password/secret/token/API key赋值做基础屏蔽，但**不是完整生产级脱敏器**。自由文本和SQL字面量仍可能带模拟姓名与客户编号，应限制目录访问，禁止接入真实客户敏感数据。X-Request-ID只接受1–64个ASCII字母/数字及 `._:-`，其他值由服务器重建，防止换行注入日志。

```text
2026-08-28T14:00:00.001+08:00 {"request_id":"req-demo","session_id":"session-demo","task_id":"task-demo","user_id":3,"role":"USER","status":"RECEIVED","state_version":0,"content":"查询当前客户人数","failure_reason":null}
```

上行为格式示例。按task_id可关联三类文件，结合阶段和工具结果核查；生成SQL不表示已经执行。

`crm/backend/src/main/resources/prompts/nl2sql-system.txt` 规定意图、澄清、MySQL 计划、权限和图表建议；`nl2sql-schema.txt` 提供可用字段及业务含义。完整姓名不加入模型可查询字段。`Nl2SqlPrompts` 再拼入当前日期、启用术语和当前身份范围。修改后重新构建/启动，不支持在线编辑。

默认日志为 `crm/backend/logs/sql-review.log`（从后端目录启动时）。每行由带时区的毫秒时间戳和 JSON 对象组成；SQL 内换行以 JSON 转义保留，避免一条 SQL 被误当成多条记录。日志不截断 SQL；请求编号、任务编号可关联任务和审计。

```text
2026-08-28T09:40:00.123+08:00 {"task_id":"示例任务编号","request_id":"示例请求编号","source":"RULE","phase":"GENERATED","sql":"SELECT c.customer_id FROM dim_customer c WHERE c.manager_id=:scopeManager LIMIT 100","parameters":{"scopeManager":"M0001"},"outcome":null}
```

该行仅为格式示例。实际 SQL 以真实日志为准，执行前后可能各有一行；同任务还可能有多次生成记录。

| JSON 字段/阶段 | 含义 |
|---|---|
| task_id / request_id | 对应任务和触发该动作的请求编号 |
| source | RULE、DEEPSEEK、TEMPLATE_FALLBACK 等计划来源 |
| sql | 本次业务查询的完整 SQL，模板保留命名参数 |
| parameters | 命名绑定参数；password、secret、token、mobile、phone、customerName 类键值替换为 [REDACTED] |
| GENERATED | 首次、修复或模板生成的待校验 SQL |
| REJECTED | 校验拒绝，outcome含业务错误码和具体原因，包括缺失范围的表/别名 |
| TOOL_RESULT | tool、round、ok、code、message及检查的sql；只代表工具预检，不能当作数据库执行 |
| EXECUTING | 即将交给 JDBC 的 SQL |
| EXECUTED | JDBC 已返回，outcome 包含返回行数 |
| SQL_ERROR | SQL 错误分类，不直接记录数据库原始错误正文 |
| TIMED_OUT / CANCELLED | 执行阶段观察到超时/取消；未进入 SQL 执行时不保证产生这一类日志 |

SQL 核查日志记录业务查询计划，不记录登录 SQL、候选定位 SQL、完整 Prompt、模型思考或 JWT。未生成业务 SQL 的澄清消息没有 SQL 日志；被取消的迟到模型返回不会继续成为执行计划。日志用于排查，不是与 MySQL 事务原子提交的审计账本。

单文件20MB，按日期/大小压缩滚动，保留14天、总量上限1GB。保留清理由滚动策略触发，不是独立的按时删除任务。日志仍可能包含 SQL 字面量和客户编号，仅限授权人员读取，不用于真实客户数据。

按任务编号筛选：

```powershell
Select-String -LiteralPath .\crm\backend\logs\sql-review.log -SimpleMatch '待核查task_id'
```

## 3. 处理流程与关键实现

### 3.1 对话与状态

```text
提交问题 + Idempotency-Key + thinking_enabled
  → 查询/锁定会话、检查幂等和活动任务
  → 同事务写任务、用户消息、助手快照和事件
  → 提交成功后异步认领任务
  → 确认客户身份 → 理解条件/意图 → 必要时澄清
  → 规则模板或模型 SQL → AST/权限/客户约束 → 必要时风险确认
  → MySQL执行 → 脱敏、指标、多图、分析
  → 终态、消息和上下文提交 → SSE发送已提交事件
```

运行阶段有 RECEIVED、INTENT_ANALYZING、SQL_GENERATING、VALIDATING、EXECUTING、REPAIRING、FALLING_BACK、PACKAGING；ASKING 和 CONFIRMING 等待用户；SUCCESS、FAILED、CANCELLED、TIMED_OUT、DEGRADED 为终态。`progress` 是阶段进度，不是模型思考比例或数据库完成百分比。

前端使用 fetch 读取 SSE，以便携带 Bearer JWT 和 `Last-Event-ID`。服务器每约350毫秒读取持久化事件，约10.5秒发送心跳，单次连接最长55秒；等待用户/终态时关闭。客户端按事件编号和任务版本去重，断线后重新订阅；连续连接异常时用状态接口恢复进度。关闭浏览器或 SSE 不等于取消查询。

每一轮澄清保留一条助手消息，该轮各阶段更新其 payload；事件表另存阶段快照。最终消息保留结果/错误。刷新后从消息快照恢复当前状态；页面内“执行阶段”列表来自本次订阅收到的阶段，不保证刷新后重建所有历史阶段列表，完整事件可按任务回放。

### 3.2 幂等、并发与取消

幂等摘要是 `session_id`、去除两端空白后的 `query_text`、`preferred_display`（缺省 AUTO）、`thinking_enabled`（缺省 true）组成的稳定 SHA-256 摘要。`X-Request-ID` 不参与摘要。数据库唯一键 `(user_id,idempotency_key)` 是最终依据，Redis 命中仍核对用户、键与摘要。数据库未自动清理任务，所以去重生命周期不只24小时，任务存在时仍有效。

提交事务使用 READ COMMITTED；同会话先取得会话行写锁，再检查活动任务。为避免 INSERT IGNORE 的锁升级死锁，会话创建采用 INSERT … ON DUPLICATE KEY UPDATE。MyBatis 本地缓存采用 STATEMENT，避免加锁后复用旧的空结果。澄清、确认、取消先锁会话，再对任务 FOR UPDATE 当前读，不复用等待锁前的 REPEATABLE READ 快照。

后台认领和每次阶段推进使用 `state_version` 条件更新；CAS 未成功即停止。状态、助手消息与 SSE 事件在同一个 MySQL 事务内提交。澄清消费对应 question_id，确认消费对应 confirm_token；重复/过期操作返回409，不再次执行。不同会话可并行；同会话的 ASKING、CONFIRMING 也占用活动任务位置。

取消接口重复调用可返回相同终态；已成功的任务不会被改成取消。执行器约200毫秒检查持久化状态，设置 JDBC `setQueryTimeout`、`setMaxRows` 并调用 `Statement.cancel`。取消返回表示不再推进，MySQL 中断有短暂传播时间。正在进行的模型 HTTP 调用不保证立刻断开，但返回结果会被丢弃，不继续 SQL/修复/降级。

消息和上下文持久化不代表工作进程崩溃后自动续跑。崩溃遗留的活动任务可在恢复服务后取消，再新提问。本版不实现持久化作业队列和自动重新调度。

### 3.3 SQL AST、安全与修复

JSqlParser 5.2 将 SQL 解析为语法树，限制单条 SELECT、长度30000字符、解析超时2秒、查询嵌套深度12及节点数量。外层必须有常量 LIMIT，默认1–100；子查询内部 LIMIT 不代替外层限制。标识符采用英文名称/别名，不接受跨库引用。

业务物理表白名单为 `dim_customer`、`fct_transaction`、`fct_product_holding`、`dim_marketing_campaign`、`fct_customer_marketing`。每张表有明确列清单，`customer_name` 完整姓名列不在自由 SQL 清单中；改别名、包函数、放到子查询也不能绕过。禁止星号投影（COUNT(*)除外）、写操作、锁定查询、注释、多语句、变量及未知函数。

| 支持 | 限制 |
|---|---|
| 非递归 CTE | CTE 内部独立验证；不能遮蔽业务表；输出列在SELECT内声明，不支持递归及CTE列名列表 |
| 派生表 | 必须有别名，内部先独立满足授权要求 |
| 关联标量/EXISTS/IN 子查询 | 校验内层对象、列，并证明其与已授权外层的关联 |
| UNION、UNION ALL | 每个分支单独验证，列数一致，整体返回上限明确 |
| INNER JOIN、LEFT JOIN | 使用明确 ON；不支持逗号/CROSS/RIGHT/FULL/NATURAL/USING JOIN |
| 聚合、CASE、常用函数、窗口函数 | 函数白名单；窗口使用内联 OVER；不支持命名窗口、DISTINCT ON、SQL_CALC_FOUND_ROWS等扩展 |

权限不再通过“某处出现了范围字符串”判定。校验器只从必定成立的 AND 等值条件提取证明，OR/NOT 内出现的限制不算授权依据。LEFT JOIN 的 ON 只能约束可空右表，不能拿右侧条件证明左表受限。客户的账号范围通过 customer_id 关联传递给事实表，营销关联再传递给活动；每个物理数据源都必须被证明受限。单客任务还要单独证明已选客户限制，不能拿经理编号冒充客户限制。

示例（结构示例，当前用户为 EAST 负责人）：

```sql
WITH scoped AS (
  SELECT c.customer_id, c.total_asset_amount
  FROM dim_customer c
  WHERE c.region_code = 'EAST'
)
SELECT scoped.customer_id,
       ROW_NUMBER() OVER (ORDER BY scoped.total_asset_amount DESC) AS asset_rank
FROM scoped
LIMIT 10
```

验证遵循无法证明就拒绝，不承诺 MySQL 全语法兼容。例如把已授权 CTE 投影列再连接到新的事实表，当前没有完整列血缘传播，可能被保守拒绝，需改写为各查询块独立受限的 SQL。AST 验证不能证明业务口径正确，也不能预测扫描成本。风险评估仍沿用可解释规则，没有 EXPLAIN 成本预算。

最终计划的安全校验失败直接结束，不通过执行错误修复放宽权限。启用工具后，模型可以在形成最终计划前根据validate_sql反馈修正SQL；此时没有执行业务SQL。仅已知 MySQL 表达错误进入最多两次修复；连接故障、权限错误、取消、超时不修复。每次修复/降级重新校验，新的风险计划需重新确认。无合适模板时 `fallback.data_available=false`，不返回替代口径数据。参考 [JSqlParser usage](https://jsqlparser.github.io/JSqlParser/usage.html)。

### 3.4 图表与分析

饼图监听容器尺寸（ResizeObserver）并同步调整ECharts画布。容器宽度小于520px或分类超过6项时收起外侧标签和引导线；宽屏少分类时保留自动避让、边缘距离和换行。所有饼图另有普通HTML完整图例，显示分类全名、原数值、单位及两位小数占比，长名称自然换行。占比仅根据本次返回的非空可加总指标计算，四舍五入可能导致显示合计不恰好为100%；不会新增分组或改变SQL结果。窄屏不再依赖可能截断的画布图例；表格仍可查看原值。参考[ECharts容器尺寸说明](https://echarts.apache.org/handbook/en/concepts/chart-size/)和[PIE标签参数](https://apache.googlesource.com/echarts-doc/+/95b341a730ff89b4bb7cb7c19d3d2641fe88958a/en/option/series/pie.md)。已测视口见第7节，不保证所有系统缩放、字体和浏览器组合都完全一致。

v1.3展示优先级：提交API显式preferred_display（非AUTO）优先，其次是模型从问题理解的preferred_display，再按实际数据判断。PIE不再受AUTO模式最多8类的启发式限制，10/12/20档均可生成；最多仍受查询返回上限约束。一个分类且人数均非负、合计大于零时可绘制饼图。排序号与唯一文字标签同时返回时，可以保留文字标签作为饼图维度，完整表格不删列；独立二维分类或重复标签不会被强行合并。均值、比例、百分数字段不能当作人数加总。无合法图形时明确说明原因，保留数据。

“0到1000万元、每100万元”不是服务器固定模板。模型从本次输入推导上下界和档宽；通用提示词要求先按客户汇总DEPOSIT持有市值，无持有按零，排除明确范围外客户，通常左闭右开、末档含上界，并在recognized_slots说明口径。分档客户数和分母都来自相同已授权范围。不使用total_asset_amount冒充存款，也不直接按持有记录数冒充人数；“0到600万元、每50万元”等不同输入由模型重新生成SQL。


v1.1 代码已经包含 BAR、LINE、AREA、PIE、SCATTER、HEATMAP，不能将用户当时只观察到柱图/表格理解成代码完全没有其他图形。是否生成取决于 SQL 返回形态、字段元数据和模型建议。本版加强选择规则与连续对话中的完整渲染。

| 数据形态 | 展示原则 |
|---|---|
| 单行/单项指标 | 指标卡与明细；明确PIE且单分类非负人数合计大于零时允许单扇区 |
| 一个分类、多项指标 | 不同指标分图，保持各自单位 |
| 时间维度 | 按时间排序折线；明确 AREA 建议且非负可用面积图 |
| 时间加分类维度 | 每个指标生成一张多系列折线，按分类对比；缺失点保留为空，不补零 |
| 少量分类、非负可加总指标 | 柱图；性别/渠道等适合构成时可补充饼图 |
| 两个数值 | 合适时散点图，编号不当数值指标 |
| 两个分类维度 | 维度组合唯一时生成热力图 |
| 重复维度、超过两个维度、无法解释的形态 | 保留指标、分析和明细，不自行聚合 |
| 指定 TABLE 或无数据 | 不生成图表 |

模型提供展示类型和字段角色建议，不能直接提交任意 ECharts 配置。后端按实际数据校验并生成 ChartSpec；一张或多张图都只消费本次结果。单客结果中的常量客户编号、姓名、快照日期不应阻止其他业务维度绘图，明细仍保留这些字段。

均值/比率不能直接求和；有可靠 customer_count/contact_count 权重时加权，否则标明返回分组均值。负数、全零、比率、均值不生成构成图。所有分析只针对最多返回的有限结果，不冒充全库统计、跨组去重、趋势预测或营销因果判断。

### 3.6 SQL工具调研、实现与调用边界

#### 3.6.1 调研与选择

| 方案 | 适用性与本版选择 |
|---|---|
| DeepSeek原生tool_calls | 当前Java适配器已使用Chat Completions，可直接定义JSON Schema并处理tool响应，无须新增模型服务；本版采用 |
| Spring AI工具调用 | 可用声明式Java工具与工具分发，但本项目已有适配器、状态机、审计和取消机制；为本次两个工具替换整个适配层收益有限，未引入新框架依赖 |
| LangChain SQLDatabaseToolkit | 提供查询、结构、表列表和查询检查工具，适合Python SQL agent；默认结构工具可能包含样本行，执行工具不会自动继承本项目的账号/客户范围与确认令牌，未直接接入 |
| MySQL EXPLAIN | 可用于后续成本评估；不是本版工具。EXPLAIN ANALYZE实际执行语句，不能作为“无执行检查”直接开放 |

依据：[DeepSeek Tool Calls](https://api-docs.deepseek.com/guides/tool_calls/)、[Thinking Mode](https://api-docs.deepseek.com/guides/thinking_mode/)、[Spring AI Tools](https://docs.spring.io/spring-ai/reference/api/tools.html)、[LangChain SQL agent](https://docs.langchain.com/oss/python/langchain/sql-agent)、[MySQL 8.4 EXPLAIN](https://dev.mysql.com/doc/refman/8.4/en/explain.html)。调研日期2026-08-28。框架功能来自官方文档，采用现有Java适配器是结合本项目约束的工程选择，不代表上述框架本身不安全。

本版实现的是**模型可调用的SQL规划/校验工具**，没有开放`execute_sql`让模型任意执行查询。模型可在形成最终计划前调用工具、得到反馈、改写SQL；实际执行仍只有平台既有JDBC入口。这一选择保留风险确认、取消和审计的一致性，并已用真实工具调用验证，不是仅在提示词中写“请检查SQL”。

#### 3.6.2 get_query_schema

| 项目 | 定义 |
|---|---|
| 用途 | 读取允许的表、列、业务口径、当前日期、当前账号范围 |
| 输入 | 空JSON对象；不接受user_id、region、密码、任意表名等参数 |
| 输出 | ok和schema字符串；内容由现有Nl2SqlPrompts与业务术语目录生成 |
| 数据来源 | 固定允许字段、启用业务术语、服务端CurrentUser；不是任意information_schema探测 |
| 数据暴露 | 不返回业务查询行、完整姓名、样本行或凭证 |

模型协议定义示例：

```json
{"type":"function","function":{"name":"get_query_schema","description":"读取允许查询的表结构、业务口径、当前账号范围；不返回客户数据。","parameters":{"type":"object","properties":{},"required":[],"additionalProperties":false}}}
```

调用参数`{}`。成功响应示例（schema按说明缩写）：

```json
{"ok":true,"schema":"当前账号范围：manager_id=M0001；允许对象及业务口径……"}
```

此工具可以多次读取，但消耗同一规划的工具次数。输入有多余字段时返回ok=false，不改变当前身份。

#### 3.6.3 validate_sql

| 项目 | 定义 |
|---|---|
| 输入字段sql | 必填string，完整单条MySQL SELECT，最多30000字符，外层有合法LIMIT |
| 输入约束 | 只允许sql字段；工具参数JSON总长度最多35000字符；空值、非对象、非法JSON均拒绝 |
| 身份绑定 | CurrentUser从JWT对应任务传入；选中客户从ModelCallContext取，模型无权声明或替换 |
| 检查器 | SqlAstValidator，与最终自由SQL的账号范围和客户限制证明使用同一实现 |
| 检查内容 | 只读、语法结构白名单、表/列/函数、外层LIMIT、逐数据源授权、已确认单客约束 |
| 不检查 | 不连接MySQL试跑，不返回行，不评估真实执行成本，不保证业务指标/分母正确 |

```json
{"type":"function","function":{"name":"validate_sql","description":"检查候选SQL；不执行SQL，不替代最终校验或风险确认。","parameters":{"type":"object","properties":{"sql":{"type":"string","description":"完整单条MySQL SELECT，最外层包含LIMIT"}},"required":["sql"],"additionalProperties":false}}}
```

输入与成功输出示例：

```json
{"sql":"SELECT c.customer_id FROM dim_customer c WHERE c.manager_id='M0001' LIMIT 100"}
```

```json
{"ok":true,"executed":false,"message":"静态预检通过；不代表业务口径或MySQL执行正确。最终SQL仍需后端校验、已确认客户校验与风险确认。"}
```

失败输出示例（提示中的表、别名、范围根据实际SQL和账号生成）：

```json
{"ok":false,"executed":false,"code":403104,"message":"SQL数据源fct_product_holding（别名h）缺少可证明的账号范围；当前账户要求客户manager_id=M0001。请通过customer_id关联受限客户，并在当前查询块添加有效范围条件；SQL未执行。"}
```

输出字段：ok为boolean；executed恒为false（合法SQL检查路径）；code为校验业务码或工具名错误字符串；message为可读诊断。未知工具返回`UNKNOWN_TOOL`，不会反射调用任意Java方法或数据库函数。静态通过不代表模型最终提交的SQL一定相同，所以最终SQL仍必须完整重验。

#### 3.6.4 实际时序与限制

```text
业务问题、受控结构和服务端范围
  → DeepSeek（tools定义、tool_choice=auto）
  → assistant.tool_calls：validate_sql(sql)
  → Java检查：ok=false + 具体缺失条件
  → role=tool、同tool_call_id返回反馈
  → DeepSeek修正并再次检查
  → 最终JSON计划（sql、columns、preferred_display等）
  → 平台最终只读/权限/客户检查
  → 高风险需用户确认 → MySQL执行 → 真实结果组装
```

默认每次规划最多3个工具续轮，另加1次最终答复请求；同轮最多4个工具调用，单次规划累计最多8个。达到续轮上限时下一请求指定tool_choice=none；模型仍要求工具或超出调用数量则以502108结束，不执行SQL。max-tool-rounds内部防御性上限为5，不建议提高默认值。工具可选择不调用，此时最终校验仍有效，不虚构“已调用工具”记录。

模型原始思考不展示、不记录。开启thinking时，DeepSeek协议要求在同一工具对话中保留assistant.reasoning_content；本版只在该次requestPlan的messages内存中回传。调用结束即释放，不写入task/context/日志。工具反馈只作为数据，不能提升权限。

首次最终内容为空或截断仍允许唯一一次响应重试，每次重试可以开启新的有界工具规划；SQL执行表达错误最多两次修复，每轮修复只启动一次有界规划，不叠加空内容重试。因此**一个用户问题不等于一次HTTP请求**。在默认上限下，单次推进过程（不含用户澄清后重新开始的规划）中，初始两次规划加两次修复理论上最多16次HTTP尝试，正常通常更少；风险确认本身不调用模型。实际次数还受取消及可选全局预算限制。

ModelCallContext把任务活动状态和已核验客户限定在当前工作线程，在finally恢复。每次HTTP和工具分发前检查活动状态；取消后不继续下一轮工具/SQL。已经发出的HTTP不保证立即中断，但迟到结果不能覆盖取消。

`MODEL_REQUEST_BUDGET_FILE`启用后，ModelRequestBudget用文件锁在每次HTTP尝试前持久化+1，多实例测试进程可共享；网络失败不退还，重启不重置，文件损坏/不可写则429102停止调用，达到上限429101停止。文件父目录须预先创建。它是本次评测的次数保护，不是token/金额预算或生产租户配额，未配置文件时不限制日常使用。

#### 3.6.5 上线与核查

默认`DEEPSEEK_TOOLS_ENABLED=true`，只有provider=deepseek且实际进入自由问题规划时才使用。兼容渠道若不支持tool_calls，设置false即可恢复无工具模式；不自动静默降级，避免隐藏渠道配置问题。工具会增加HTTP次数和延迟，不能承诺所有问题准确率或响应速度都提升。此次选择依据为第7节同一隔离库的小样本SQL结果对照，仍须按真实业务测试集继续评估。

日志的TOOL_RESULT记录工具名、轮数、ok、code、message与被检查SQL，执行日志GENERATED/REJECTED/EXECUTING/EXECUTED另行记录。定位问题时先看预检失败，再看最终SQL是否被拒绝，最后检查执行及结果，不能以TOOL_RESULT.ok=true代替执行成功。

关键代码：`model/SqlPlanningTools.java`定义工具；`model/DeepSeekModelAdapter.java`处理协议与有界循环；`model/ModelCallContext.java`绑定生命周期和单客上下文；`model/ModelRequestBudget.java`计数；`execution/application/SqlAstValidator.java`实际验证；`conversation/application/QueryTaskProcessor.java`最终统一执行编排。

| deleted_at | DATETIME(3) | 是 | V6新增；NULL为可见，非空为逻辑删除时间，不物理删除消息/任务/审计 |

索引idx_session_user_updated(user_id,updated_at)，V6新增idx_session_visible(user_id,deleted_at,updated_at)，V8新增idx_session_created(user_id,deleted_at,created_at,session_id)用于本人可见会话的创建顺序查询。新任务的上下文取自服务器持有的此表，不采信客户端自报的客户范围。

### 4.13 conversation_message：持久化消息（V5新增）

| 字段 | 类型 | 可空 | 中文含义与说明 |
|---|---|---|---|
| message_id | BIGINT AUTO_INCREMENT | 否 | 全局消息主键，作为游标 |
| session_id | VARCHAR(36) | 否 | 所属会话 |
| task_id | VARCHAR(36) | 否 | 所属任务 |
| role_code | VARCHAR(16) | 否 | USER或ASSISTANT |
| message_key | VARCHAR(100) | 否 | 同任务操作键：query、answer-问题编号、confirm-令牌、assistant-轮数；V8旧回复恢复使用legacy-answer |
| content | TEXT | 否 | 用户输入或助手简要阶段说明 |
| payload_json | JSON | 是 | 助手完整TaskStatus快照，用户消息为空 |
| created_at | DATETIME(3) | 否 | 消息创建时间 |
| updated_at | DATETIME(3) | 否 | 助手消息最近更新时刻 |
| feedback_code | VARCHAR(8) | 是 | V8新增；本人对助手消息的LIKE或DISLIKE，无评价为NULL |
| feedback_updated_at | DATETIME(3) | 是 | V8新增；最近评价/取消评价时间，不改变消息时间及会话顺序 |

唯一键uk_message_operation(task_id,message_key)，索引idx_message_session(session_id,message_id)，V8新增idx_message_chronology(session_id,created_at,message_id)。消息按创建时间及编号复合顺序分页，不能只按编号排列后来补入的旧回复。同一澄清轮的助手消息原位更新，新的用户回答和下一轮助手消息另建记录。用户输入的虚构姓名可能仍保留在自由文本中，此表不是生产级敏感信息隔离层。

### 4.14 query_task_event：持久化阶段事件（V5新增）

| 字段 | 类型 | 可空 | 中文含义与说明 |
|---|---|---|---|
| event_id | BIGINT AUTO_INCREMENT | 否 | 全局事件主键，SSE的id及Last-Event-ID |
| task_id | VARCHAR(36) | 否 | 关联任务 |
| state_version | BIGINT | 否 | 对应任务版本 |
| payload_json | JSON | 否 | 已提交TaskStatus完整快照 |
| created_at | DATETIME(3) | 否 | 事件写入时刻 |

唯一键uk_task_event_version(task_id,state_version)，每次成功状态提交只对应一条事件。读取按task_id及event_id过滤，升序每批最多100条。事件不是模型token，也不包含原始思考正文。

### 4.15 数据关系与迁移

业务编号关系沿用v1.1：交易、产品持有关联客户；营销触达关联客户及活动；客户关联经理。会话按user_id隔离，一个会话包含多个任务，一个任务包含用户/助手消息和阶段事件。全部关系当前仍无物理外键，应用事务和生成器维持一致性。

V1创建11张业务/平台表，V2初始化术语，V3扩展查询计划，V4增加版本/修复/图表字段，V5增加完整虚构姓名、任务幂等/上下文字段及3张会话相关表。V6为conversation_session增加deleted_at及可见性索引；V7只更新dim_customer的虚构完整姓名和脱敏名。没有新增工具会话表：工具上下文只在后端调用内存中存在。当前共14张业务/平台表，另有Flyway自己的flyway_schema_history技术表。

V5只为历史session_id中唯一归属一个user_id的任务回填会话和原始USER消息；不回填臆测的历史助手过程和上下文。历史共有session_id若属于多个用户，不建立共享会话。历史任务和query_history原表不删除。

V8增加上述反馈字段和时间排序索引，并修复V5只补USER导致旧会话回答缺失的问题。仅处理idempotency_key为NULL、归属与会话所有者一致、会话未删除且该任务没有ASSISTANT消息的旧任务。恢复query_task.result_json及已保存状态/错误，使用任务更新时间作为旧回复时间；没有完整结果时只恢复摘要并附说明。不会调用模型、执行旧SQL、补造阶段事件、开放旧确认令牌或推测上下文。已有助手消息不重复回填，已删除会话不恢复。迁移新增0张业务表，仍为14张业务/平台表。不要修改已应用迁移或手动重复执行ALTER TABLE。

数据库默认utf8mb4_0900_ai_ci；幂等键单独使用ASCII二进制排序规则以区分大小写。新会话表毫秒时间用于展示和排序，不作为并发控制依据；并发依赖锁、唯一键和版本。

## 5. API 详细示例与数据字典

### 5.1 通用约定

默认根地址 `http://127.0.0.1:8080`，本机验收用18080。JSON使用 snake_case，空的可选对象字段通常省略。除登录和健康检查外要求 `Authorization: Bearer <access_token>`；身份只从 JWT 获取，客户端不得指定可覆盖权限的用户/机构编号。`X-Request-ID` 可选（1–64位ASCII字母/数字或 `._:-`，无效时服务端生成）。版本仍使用 `/api/v1` 路径，应用版本是1.3.0。

除SSE外，成功返回 HTTP200 和统一封装：

```json
{"code":0,"message":"处理成功","data":{},"request_id":"请求编号"}
```

提交必须提供 `Idempotency-Key`。澄清/确认不依赖该头去重，而是消费当前问题编号/确认令牌。完整机器可读契约见 [OpenAPI](../contracts/openapi/crm-nl2sql-mvp-v1.yaml)。

### 5.2 登录与当前用户

`POST /api/v1/auth/login`：username必填≤64字符、password必填≤128字符。

```json
{"username":"director01","password":"Demo@123"}
```

响应的data结构示例：

```json
{"access_token":"JWT字符串","token_type":"Bearer","expires_in":28800,"user":{"user_id":3,"username":"director01","display_name":"演示负责人","role":"ORG_MANAGER","region_code":"EAST","branch_id":"B001"}}
```

`GET /api/v1/auth/me` 无请求体，data为同样的user结构。role为 CUSTOMER_MANAGER、TEAM_LEAD、ORG_MANAGER；manager_id、branch_id 依角色可空。登录失败/令牌失效为401001。

### 5.3 提交问题

`POST /api/v1/queries`，请求头示例 `Idempotency-Key: 50b06f3a-43fa-42db-9e20-1ead78015a49`。

| 请求字段 | 类型 | 必填/默认 | 说明 |
|---|---|---|---|
| session_id | string | 必填 | ≤36字符，建议UUID；新编号首次提交时创建会话 |
| query_text | string | 必填 | 非空，≤1000字符；提交时去两端空白 |
| preferred_display | string | AUTO | AUTO、TABLE、BAR、LINE、AREA、PIE、SCATTER、HEATMAP、METRIC；非AUTO显式选择优先，最终图形仍须适合实际数据 |
| thinking_enabled | boolean | true | 本任务固定思考设置 |
| Idempotency-Key（头） | string | 必填 | 8–128个ASCII字母/数字或 `._:-`，区分大小写 |

```json
{"session_id":"11111111-1111-4111-8111-111111111111","query_text":"统计近30天各机构客户交易金额","preferred_display":"AUTO","thinking_enabled":true}
```

响应data：

```json
{"task_id":"22222222-2222-4222-8222-222222222222","session_id":"11111111-1111-4111-8111-111111111111","status":"RECEIVED","progress":0,"status_url":"/api/v1/queries/22222222-2222-4222-8222-222222222222/status"}
```

重复键+相同请求返回同一task_id及其当前状态，可能已经完成；不同内容返回HTTP409/code409005。同会话有活动任务、但使用新键提交时返回409006。同键同内容即使已有活动任务仍可重放原响应；所属会话被删除后禁止重放，返回404001。不同用户的相同键互不冲突，但不能共用对方的session_id。

### 5.4 任务状态与结果

`GET /api/v1/queries/{taskId}/status`，data为TaskStatus。

| 字段 | 类型 | 说明 |
|---|---|---|
| task_id / session_id | string | 任务/会话编号 |
| status | string | 第3.1节列出的15种状态 |
| progress | integer | 0–100阶段进度 |
| message | string | 可展示简要说明 |
| intent | string，可选 | CUSTOMER_FILTER、TRANSACTION_ANALYSIS、PRODUCT_HOLDING、MARKETING_ANALYSIS、GENERIC_ANALYSIS、UNKNOWN |
| clarification_round | integer | 已完成澄清轮数，从0开始 |
| question | object，可选 | 等待补充的问题 |
| confirmation | object，可选 | 当前风险确认信息 |
| result | object，可选 | QueryResult |
| error | object，可选 | `message`可读错误，无原始数据库错误/密钥 |
| repair_attempts | integer | 已消耗修复次数，0–2 |
| execution_timeout_seconds | integer | SQL执行超时配置 |
| cancellable | boolean | 是否可取消；等待补充/确认也是true |
| state_version | integer(int64) | 持久化版本，客户端忽略较旧版本 |
| thinking_enabled | boolean | 本任务思考设置 |
| display_query | string，可选 | 当前有效问题，客户确定后附客户编号，前端加“当前查询内容为：” |

TaskStatus另有可选created_at和updated_at（任务创建、最近推进时间，ISO本地日期时间）；新快照提供，旧快照可能缺失。V8恢复快照另有legacy_recovered=true及legacy_notice，分别表示恢复标记及原结果是否完整的说明，不代表重新执行成功。日期时间按当前部署时区存储，现有LocalDateTime接口不带偏移；页面按浏览器本地时间解释，部署与使用环境应统一时区。消息操作显示的时间优先使用消息本身字段，见5.12节。

候选客户状态示例（全部虚构，编号为结构示例）：

```json
{
  "task_id":"22222222-2222-4222-8222-222222222222",
  "session_id":"11111111-1111-4111-8111-111111111111",
  "status":"ASKING","progress":30,"message":"请确认要查询的客户；选择前不会查询资产或交易信息。",
  "clarification_round":0,"repair_attempts":0,"execution_timeout_seconds":60,
  "cancellable":true,"state_version":2,"thinking_enabled":true,
  "display_query":"帮我查找一下李先生的资产信息",
  "question":{
    "question_id":"33333333-3333-4333-8333-333333333333",
    "type":"CUSTOMER_SELECTION",
    "prompt":"请确认要查询的客户；选择前不会查询资产或交易信息。",

```

question通用字段：question_id、type、prompt、options(string[])、recognized_slots(object)、candidates(array)。type继承MISSING_TOPIC、MISSING_TIME_RANGE、TIME_BASIS、CONFLICT、MODEL_CLARIFICATION，并新增 CUSTOMER_IDENTITY、CUSTOMER_SELECTION、CUSTOMER_NOT_FOUND、FOLLOWUP_CONTEXT。候选项最多10个，字段仅customer_id、name、branch_id、mobile，没有资产、年龄等客户画像。

### 5.5 SSE事件

`GET /api/v1/queries/{taskId}/events`，请求头携带JWT；可传 `Last-Event-ID: 123`，缺省0，从该编号之后继续。响应类型 `text/event-stream`，没有ApiResponse外层。

```text
id: 124
event: status
data: {"task_id":"22222222-2222-4222-8222-222222222222","session_id":"11111111-1111-4111-8111-111111111111","status":"EXECUTING","progress":75,"message":"正在查询已授权的营销数据","clarification_round":0,"repair_attempts":0,"execution_timeout_seconds":60,"cancellable":true,"state_version":5,"thinking_enabled":true,"display_query":"统计近30天各机构客户交易金额"}

:heartbeat

```

`event:status` 的data是完整TaskStatus，id来自全局自增event_id，单任务可能不连续。没有新事件且任务已经等待/结束时发送 `event:snapshot`，不带id，然后关闭。断开后用最后收到的id重连；不把断线、连接55秒超时或心跳当成任务失败。终态错误仍在data的status/error中；SQL未开始或失败都可能没有result。

### 5.6 回答反问、确认与取消

`POST /api/v1/conversations/{sessionId}/messages`：

```json
{"task_id":"22222222-2222-4222-8222-222222222222","question_id":"33333333-3333-4333-8333-333333333333","answer_text":"C00000001","selected_options":[]}
```

task_id、question_id必填，answer_text非空时优先，或使用selected_options。CUSTOMER_IDENTITY/CUSTOMER_NOT_FOUND等身份补充问题必须带identity_type；CUSTOMER_SELECTION候选选择不要求此字段。候选选择把编号放入answer_text，服务端验证它属于本轮候选且仍有权限。成功data与提交响应一致，继续订阅原任务。普通独立追问请重新POST `/queries` 并沿用session_id，不能用messages接口创建新任务。

身份补充响应中的question与请求示例：

```json
{"question_id":"33333333-3333-4333-8333-333333333333","type":"CUSTOMER_IDENTITY","prompt":"请选择一种身份信息后补充","options":[],"recognized_slots":{},"candidates":[],"input_types":["CUSTOMER_ID","CUSTOMER_NAME","MOBILE_SUFFIX"]}
```

```json
{"task_id":"22222222-2222-4222-8222-222222222222","question_id":"33333333-3333-4333-8333-333333333333","identity_type":"MOBILE_SUFFIX","answer_text":"0012","selected_options":[]}
```

| 字段/值 | 类型/验证 | 说明 |
|---|---|---|
| question.input_types | string[] | 身份补充问题允许的类型；非身份问题与候选选择为[] |
| identity_type | string，可选但身份补充必填 | CUSTOMER_ID、CUSTOMER_NAME、MOBILE_SUFFIX；普通业务澄清无需填写 |
| CUSTOMER_ID | `C`后8位数字 | 客户编号；不是手机号或任意数字 |
| CUSTOMER_NAME | 2–4个中文字符 | 本项目模拟的完整姓名，不是“陈先生”；前端称客户虚拟姓名 |
| MOBILE_SUFFIX | 恰好4位数字的字符串 | 保留0012之类的前导零，结合原始客户姓名线索定位；缺少姓名线索会要求改用编号/姓名 |
| CUSTOMER_SELECTION | answer_text为候选编号 | 仅允许本轮候选，不接受任意编号；不显示通用身份输入框 |

格式错误返回400006，不消耗当前question_id，也不执行查询，用户可在原问题继续填写。即使输入完整姓名或后四位，仍只查询授权范围内候选，不返回权限外客户是否存在。

`POST /api/v1/queries/{taskId}/confirmations`：

```json
{"confirm_token":"当前任务返回的随机令牌","decision":"CONFIRM","reason":"演示分析需要"}
```

confirm_token和decision必填，decision为CONFIRM或REJECT，reason为兼容可选字段，当前不参与权限判断。confirmation对象字段为confirm_token、risk_level(MEDIUM/HIGH)、message、reasons(string[])。确认只执行保存的计划，不重新生成SQL；REJECT调用取消。成功返回TaskStatus。令牌随状态消费，没有单独时间过期字段。

`POST /api/v1/queries/{taskId}/cancel` 无需请求体，返回TaskStatus。已终态时返回原终态；重复取消不新增业务执行。

### 5.7 完整会话与上下文

`GET /api/v1/conversations?page_no=1&page_size=30`：page_no≥1，page_size为1–100。data直接为数组，没有total；按created_at DESC、session_id DESC排序。前端用返回是否满页决定是否继续加载，最后一次可能返回空页。

```json
[{"session_id":"11111111-1111-4111-8111-111111111111","title":"统计近30天各机构客户交易金额","state_version":2,"created_at":"2026-08-28T09:00:00","updated_at":"2026-08-28T09:00:01"}]
```

`active_task_id` 可空，表示待处理任务；title来自首条问题前160字符，不由模型生成，不支持重命名。

`GET /api/v1/conversations/{sessionId}?before_message_id=0&page_size=100`：默认返回最近100条消息，响应内部按created_at、message_id升序；用本页首条消息的message_id作为before_message_id继续获取更早一页（不是最小编号）。before≤0按最新页处理，page_size为1–100。has_more是“本页数量达到上限”的提示，不是精确总量。

data示例（payload在此简写；实际为完整TaskStatus）：

```json
{
  "session_id":"11111111-1111-4111-8111-111111111111",
  "title":"统计近30天各机构客户交易金额","state_version":2,
  "context":{"query":"统计近30天各机构客户交易金额","source_task_id":"22222222-2222-4222-8222-222222222222"},
  "messages":[
    {"message_id":101,"task_id":"22222222-2222-4222-8222-222222222222","role_code":"USER","content":"统计近30天各机构客户交易金额","created_at":"2026-08-28T09:00:00"},
    {"message_id":102,"task_id":"22222222-2222-4222-8222-222222222222","role_code":"ASSISTANT","content":"查询完成","payload":{"status":"SUCCESS"},"created_at":"2026-08-28T09:00:00"}
  ],
  "has_more":false
}
```

context字段为query、customer_id（可空）、source_task_id（可空）。它只描述最后一个可用查询的条件和已确认客户，不含查询行数据或模型思考，也不作为客户端可修改的权限来源。用户只能读取自己的会话；无此会话与他人会话均返回404001。

消息详情额外返回updated_at和feedback。USER按created_at显示发送时间，ASSISTANT按updated_at显示最近回复时间；不是打开页面的当前时刻。feedback为LIKE、DISLIKE或NULL。分页先查询游标在当前会话中的时间，再用(created_at,message_id)比较；其他会话或不存在的游标返回400001，避免迁移后补入的较大编号扰乱旧消息顺序。

### 5.8 QueryResult、图表与分析字典

| QueryResult字段 | 类型 | 说明 |
|---|---|---|
| result_type | string | 计划展示类型，实际以charts为准 |
| title / summary | string | 标题与结果概况 |
| columns | ColumnMeta[] | 实际结果列元数据 |
| rows | object[] | 已处理客户字段的结果行，键对应columns.key |

### 5.11 删除会话与消息导航目录

`DELETE /api/v1/conversations/{sessionId}`，无需请求体：

```json
{"code":0,"message":"处理成功","data":{"session_id":"11111111-1111-4111-8111-111111111111","deleted":true},"request_id":"delete-demo"}
```

只允许本人操作；不存在/他人会话返回HTTP404/code404001，有active_task_id返回HTTP409/code409007。数据库行锁保护删除与提交的竞争。本人重复删除同一已删除会话返回相同成功语义，仅产生一条CONVERSATION_DELETED审计。

删除后会话列表、详情、导航目录、旧任务status/events、确认/取消/澄清及原幂等键重放均不可再打开会话；新问题也不能复用已删session_id。旧query-history入口同时隐藏该会话相关记录。conversation_message、query_task、query_task_event和audit_event保留，不能把此功能当作审计清除或隐私数据物理擦除。没有恢复/回收站接口。

`GET /api/v1/conversations/{sessionId}/anchors?after_message_id=0&page_size=100`：

| 参数/字段 | 类型 | 说明 |
|---|---|---|
| after_message_id | int64，默认0 | 非负游标，0取首批；否则按游标对应消息的created_at、message_id复合顺序取后续USER消息 |
| page_size | integer，默认100 | 1–100 |
| data | array | 按created_at、message_id升序，无total/has_more包装 |
| message_id | int64 | 持久化用户消息编号，用于定位DOM及正文分页 |
| content | string | 已持久化的用户输入文本，不包含助手图表结果 |
| created_at | string | 消息创建时间，目录与正文保持相同时间顺序 |

```json
{"code":0,"message":"处理成功","data":[{"message_id":101,"content":"统计近30天各机构客户交易金额","created_at":"2026-08-28T09:00:00"},{"message_id":108,"content":"改成近7天","created_at":"2026-08-28T09:05:00"}],"request_id":"anchors-demo"}
```

返回满页时用最后message_id继续加载；末页可能需要额外一次空数组请求。参数非法400001，会话不可见404001。点击目录后前端按5.7节before_message_id补齐更早正文并滚动定位，不重新提交问题或执行SQL。

### 5.12 回复评价与消息操作

`POST /api/v1/conversations/{sessionId}/messages/{messageId}/feedback`，需要JWT，无需Idempotency-Key：

```json
{"feedback":"LIKE"}
```

```json
{"code":0,"message":"处理成功","data":{"message_id":102,"feedback":"LIKE"},"request_id":"feedback-demo"}
```

| 字段/行为 | 类型与约束 |
|---|---|
| sessionId | 本人未删除会话编号 |
| messageId | 同会话内持久化ASSISTANT消息编号，int64；USER消息不能评价 |
| feedback（请求） | 必填枚举LIKE、DISLIKE、NONE；NONE取消评价，数据库保存NULL |
| data.feedback（响应） | 本次保存的枚举，取消时为NONE；详情接口无评价时为NULL |
| 可评价状态 | ASKING、CONFIRMING、SUCCESS、FAILED、CANCELLED、TIMED_OUT、DEGRADED |
| 互斥与重复 | 每条回复最多一种评价；前端再次点击同项发送NONE，切换发送另一项；同值重复提交仍为同值 |
| 权限与错误 | 非本人/已删除会话、非本会话消息或USER消息404001；非法枚举400001；生成中的回复409008 |
| 持久化与并发 | 与删除共用会话行锁，仅更新feedback_code与feedback_updated_at，不修改会话/消息时间，不调用模型或执行查询 |

前端即时SSE消息若尚无数据库编号，先从本人会话详情匹配task_id及clarification_round再提交评价；未同步则提示稍后重试，不伪造编号。没有公开点赞数、评价管理台或将评价自动用于模型训练。

用户消息下方显示“HH:mm、复制、编辑”；时间悬停显示完整日期。点击编辑将该条原文放入底部输入框并聚焦，修改后按正常提交接口发送新消息，原消息与回答保留；新提交使用新幂等键。当前有活动任务时编辑不可用，需先完成或取消，不隐式中断后台查询；编辑不是修改历史记录或重建对话分支。

助手消息下方显示“复制、点赞、点踩、HH:mm”。复制为纯文本，包含已保存的标题、摘要、指标、分析、建议、表格明细和SQL预览；澄清回复包含提示及选项。复制不会查询数据库；剪贴板权限失败时提示手动选择。旧结果缺失数组/analysis时仅补空容器便于渲染，TABLE结果默认显示明细；不补造数值、日期或来源，旧版未保存的信息明确标注。

账号切换会卸载旧会话界面，停止旧订阅，并使用固定账号前缀保存恢复键；跨标签页通过storage事件清空旧身份后重新验证。HTTP请求比较请求时令牌与响应时令牌，不一致即丢弃，包括迟到的401，避免清掉新账号令牌。409009仅是前端本地“账号已切换”错误，不是服务端业务错误码。最终会话、消息、任务、导航和评价仍由后端JWT所有权校验，不能仅依靠前端隐藏。

### 7.2 真实模型对照与局限

详细记录见[本版测试报告](testing/v1.3验证记录.md)与[追加需求验证](testing/v1.3追加需求验证记录.md)。所有外部HTTP尝试共用计数文件，首次请求、重试和工具续轮都计数，不超过本次授权50次。mock、协议替身及MySQL测试不消耗外部额度。

测试用独立算法生成标准答案，不把标准SQL或答案发给模型。先按账号限定客户，再按客户汇总DEPOSIT市值，Python计算分档和分母；与实际SQL逐档人数/比例/图形比对。随机样本外补充0、阈值前0.01、恰好阈值、恰好上限、上限+0.01及一客多持有等边界，另有权限外数据。性别/交易使用独立聚合标准答案。

早期随机数据评测未覆盖超过上限的客户，曾漏掉模型额外统计上限外分组的问题；不能把当时的通过率当作质量结论。补充边界后修正通用范围提示，并再次运行相同用例。工具组又暴露排序号被当作第二分类导致未生成PIE的问题，已通过通用结果组装修复并加入回归测试。最终报告保留不同阶段证据，不隐藏失败。

评分包括：behavior_correct（预期终态/反问类型）、result_correct（实际人数/金额/比例对独立答案）、chart_correct（请求展示是否出现）、sql_validation_passed（后端保存通过校验的计划）、sql_executed（执行日志证据）。sql_generated含被拒绝的候选SQL；日志缺失且无已保存SQL时为null，不能猜测未生成。比较器无法识别列/区间时判失败待人工核查，不因SQL执行成功自动判对；不做要求逐字相同的SQL字符串匹配。

小样本一次通过不表示所有自由问题稳定准确；模型输出、远端版本及样本分布都会影响结果。工具增加请求量和延迟，默认开启是基于本次对照结果的选择，保留关闭开关。

### 7.3 复验、升级与数据安全

自动脚本、依赖安装、隔离库准备、边界数据和真实模型额度设置见[scripts/evaluation/README.md](../scripts/evaluation/README.md)。入口为`scripts/verify-v1.3.ps1`，默认只做不调用真实模型的构建/单元验证；MySQL、HTTP与真实模型评测需显式选择。

升级顺序：备份模拟库和配置；完成/取消旧任务；停止旧后端；构建同版本前后端；启动1.3后端自动执行尚未应用的V6/V7/V8；启动前端并检查健康、登录、身份补充、饼图、删除及日志。已有local配置覆盖默认值，核对tools-enabled、token和超时，不覆盖现有密钥。V7更新模拟完整姓名，旧会话文字不回写，已选择的customer_id及资产关联不变。

本次交付为代码、测试与文档；没有替换用户正在运行的18080旧实例。临时验证服务不作为正式部署。回滚前检查协议差异，保留迁移记录，不直接删除Flyway历史；旧前端不能提供本版identity_type，应配套升级。

日志是授权运维资料，不随仓库提交；配置日志目录持久卷、磁盘空间监测和访问权限，应用日志写入失败不能替代监控告警。消息/事件结果快照尚无自动过期，需规划备份和保留期。LIMIT只限制返回量，不保证扫描量；静态检查不能代替指标口径复核。测试脚本只允许本地后端和_test库，但提交后才核对后端任务所在库，启动时仍必须检查实例配置，禁止误指用户工作实例。
