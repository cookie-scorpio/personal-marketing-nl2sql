# 认证、注册与统一授权说明

本文说明本项目新增的注册、强密码、浏览器 RSA 密码保护和统一授权中心。该设计适用于当前本机 `localhost` 演示环境；管理员审批和角色分配界面不在本次范围内。

## 目标与边界

新增功能解决四件事：

- 未有账号的用户可提交注册申请；申请只创建待审批账号，不能立即登录或查询数据。
- 用户名与密码在前后端执行一致的规则校验，后端校验是最终依据。
- 登录和注册中的密码在浏览器中使用 RSA-OAEP-SHA-256 加密，后端使用当前进程的 RSA 私钥解密后校验或哈希。
- 认证、资源归属和客户行级数据范围收敛到统一授权中心，查询、会话和历史模块不再各自维护角色范围规则。

本次没有实现管理员审批、角色分配、密码找回、短信或邮件验证码、登录限流和 HTTPS 证书部署。注册接口也不接收角色、区域、网点、客户经理等字段。

## 账号状态与数据变化

新增 Flyway 迁移 [V14__add_pending_registration_account_status.sql](../crm/backend/src/main/resources/db/migration/V14__add_pending_registration_account_status.sql)。迁移不修改已发布的历史迁移，完成以下变化：

| 字段 | 已有账号 | 新注册账号 |
|---|---|---|
| `account_status` | `ACTIVE` | `PENDING` |
| `enabled` | `true` | `false` |
| `role_code` | 既有业务角色 | `NULL` |
| `region_code`、`branch_id`、`manager_id` | 既有范围 | `NULL` |
| `password_hash` | BCrypt 哈希 | BCrypt 哈希 |

保留 `role_code`、`region_code` 可空，是为了准确表达“尚未分配权限”。待审批账号不会被转换为 `CurrentUser`，不会签发 JWT，因此不存在“空范围却可访问接口”的路径。

未来管理员功能应在一个事务中完成：写入角色和对应范围、将 `account_status` 设为 `ACTIVE`、将 `enabled` 设为 `true`。在此之前，待审批账号用正确密码登录仍会收到“账号待审批，暂不可登录”。

## 用户名与强密码规则

用户名沿用演示账号 `manager01`、`leader01`、`director01` 的形式：

- 4 至 64 位；
- 小写英文字母开头，数字结尾；
- 只允许小写英文字母和数字，格式为 `^[a-z]+[0-9]+$`；
- 前端会转小写并即时提示，后端会再次规范化和校验；数据库唯一索引仍是并发场景下的最终约束。

密码规则如下：

- 至少 8 位；
- 必须同时有数字、小写字母、大写字母和非空白特殊符号；
- UTF-8 编码不得超过 72 字节，避免 BCrypt 的输入截断问题；
- 只在内存中用于一次校验和 BCrypt 哈希，绝不写入日志、JWT、数据库明文字段或接口响应。

前端规则只用于帮助用户一次完成填写；绕过前端、直接调用接口时，`PasswordPolicy` 仍会拒绝不合格密码。

## 密码加密与数据处理流程

密码保护的主链路如下：

```text
注册/登录页
  -> GET /api/v1/auth/public-key，获取 SPKI Base64 公钥和 key_id
  -> Web Crypto 导入公钥，RSA-OAEP-SHA-256 加密密码
  -> POST /api/v1/auth/register 或 /login，仅发送 key_id + encrypted_password
  -> RsaPasswordCipher 按 key_id 用配置私钥或本地临时私钥解密
  -> 注册：校验强密码 -> BCrypt 哈希 -> 写入 PENDING 账号
  -> 登录：校验 BCrypt 哈希与账号状态 -> 签发 JWT（仅 ACTIVE 账号）
```

未设置 `AUTH_RSA_PRIVATE_KEY` 时，后端会在本机启动时生成一对 2048 位 RSA 临时密钥。私钥只存在于该后端进程的内存中，重启后即失效；前端总是从当前后端获取公钥，因此仓库刚拉取下来也可以直接启动和联调，无需分发私钥文件。

如需固定密钥，`AUTH_RSA_PRIVATE_KEY` 应为 PKCS#8 PEM RSA 私钥。后端从私钥推导公钥，生成公钥摘要作为 `key_id`；前端不会拥有私钥。服务重启或轮换密钥后，旧 `key_id` 的请求会被拒绝，页面刷新后会重新获取公钥。

建议使用至少 2048 位 RSA 私钥。例如可由运维在安全终端生成，再把内容写入部署环境变量：

```powershell
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out auth-rsa-private.pem
```

固定密钥的配置项：

```text
AUTH_RSA_PRIVATE_KEY=<PKCS#8 PEM 私钥；多行或使用 \n 均可>
JWT_SECRET=<至少32字节的随机密钥>
```

当前仓库刻意不提交固定私钥：本地临时密钥已满足开发联调，且避免代码副本长期携带可复用的私钥。需要部署到共享环境时，应配置固定私钥并设置 `AUTH_ALLOW_EPHEMERAL_RSA_KEY=false`，使缺失或无效密钥的应用拒绝启动。私钥不可放入前端 `.env`、MySQL、Redis 或日志。

RSA 报文加密不能替代 HTTPS。当前方案只保证本机 `localhost` 可使用，因为浏览器 Web Crypto 在普通局域网 HTTP 地址下通常不可用。切换到局域网或生产地址之前，必须配置 HTTPS，并继续保留 RSA 加密作为额外保护层。

## 接口说明

所有接口仍使用既有的 `ApiResponse` 信封：`code`、`message`、`data`、`request_id`。字段名遵循 snake_case。

### 获取公钥

`GET /api/v1/auth/public-key` 不需要 JWT。

响应 `data`：

```json
{
  "key_id": "公钥摘要前16位",
  "algorithm": "RSA-OAEP-256",
  "public_key": "SPKI格式公钥的Base64编码"
}
```

### 提交注册

`POST /api/v1/auth/register` 不需要 JWT。

请求体：

```json
{
  "display_name": "张三",
  "username": "zhangsan01",
  "password": {
    "key_id": "与公钥响应一致",
    "encrypted_password": "RSA密文的Base64编码"
  }
}
```

成功时返回 `username`、`display_name`、`account_status: "PENDING"` 和待审批提示。用户名冲突返回 `409010`；用户名、姓名、密码或密文格式错误返回对应的 `40001x` 错误。注册成功不返回 token。

### 登录

`POST /api/v1/auth/login` 的 `username` 和加密密码信封结构与注册一致。`ACTIVE` 且启用的账号登录成功后返回 JWT；凭据正确但状态为 `PENDING` 时返回 `403101`。未知账号和密码不正确仍统一返回 `401001`，避免枚举账号。

`GET /api/v1/auth/me` 保持不变，需要 Bearer JWT。

## 统一授权中心

认证和授权分为三个层次：

```text
JwtAuthenticationFilter
  验签 JWT，构造可信 CurrentUser
          |
AuthorizationCenter
  校验已认证身份、资源归属、取得数据范围
          |
DataScopePolicy
  唯一的角色 -> 客户行级范围映射
          |
会话 / 查询 / 历史 / SQL规划 / 客户检索 / 模型SQL AST校验
```

`DataScopePolicy` 是角色数据范围的唯一规则源：

| 角色 | 客户过滤条件 |
|---|---|
| `CUSTOMER_MANAGER` | `manager_id = 当前 manager_id` |
| `TEAM_LEAD` | `branch_id = 当前 branch_id` |
| `ORG_MANAGER` | `region_code = 当前 region_code` |

`AuthorizationCenter` 统一执行三类判断：

- `requireAuthenticated`：验证已存在可信 `CurrentUser`，并检查该身份的范围字段完整；
- `requireOwner`：会话、查询任务和历史记录只能由资源所属用户访问。失败时统一按资源不存在处理，避免泄露他人资源；
- `customerScope` / `customerCondition`：向客户检索、规则 SQL 和名单校验提供同一个行级范围。

模型提示词、SQL AST 校验也改为读取同一份 `DataScopePolicy` 映射。SQL 层仍保留 AST 白名单和范围证明，这是纵深防御，不会因为授权中心存在而删除。

## 前端交互说明

注册入口位于现有登录卡片的“没有账号？申请注册”。页面沿用既有深酒红介绍区、浅色表单区、Element Plus 输入框和主操作按钮：

- 登录状态保留演示账号快捷选择；
- 注册状态只呈现姓名、用户名、密码和确认密码，避免制造无用的角色或范围选择项；
- 密码规则以紧凑状态标签实时反馈；
- 注册成功后显示明确的“待审批、不可登录”结果，并提供返回登录按钮；
- 异步提交时使用原有按钮 loading 状态，错误使用统一的红色提示框。

前端每次登录/注册会从 `passwordCrypto.ts` 获取或复用当前公钥，只向 `apiRequest` 传递密文。账号状态恢复、JWT 存储与 401 退出登录的既有逻辑保持不变。

## 验证方式

后端新增单元测试覆盖用户名与强密码规则、RSA-OAEP 加解密、待审批账号写入以及统一资源归属判断。完整验证命令：

```powershell
Set-Location crm/backend
mvn test

Set-Location ../frontend
npm run type-check
npm test
npm run build
```

手工验收时，通过 `localhost` 启动服务即可；本地启动脚本会临时生成 `JWT_SECRET`，后端也会生成进程内 RSA 密钥。提交一个符合规则的新账号后，应看到待审批提示；使用该账号和正确密码登录，应被拒绝；原有三个演示账号应仍可成功登录并只看到各自的数据范围。
