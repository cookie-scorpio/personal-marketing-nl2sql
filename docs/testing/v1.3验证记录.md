# v1.3 验证记录

日期：2026-08-28。此文区分程序测试、真实模型小样本及人工浏览器检查。所有业务数据为虚构；原用户库pf_nl2sql和原18080实例未改动。

## 环境与数据

JDK17、Spring Boot4.1.1、Maven3.9.16、MySQL8.4、单节点Redis7、Vue3/TypeScript/Element Plus。独立库pf_nl2sql_v13_test；模型provider=deepseek、沿用本地配置模型deepseek-v4-flash、thinking=true、max_tokens=16384、retry_max_tokens=32768、读取超时120秒。密钥、密码未写入报告。

数据生成种子20260826，10000客户、30000交易、20000持有、20活动，另有集成测试夹具及19个固定金额边界/权限外客户。按客户聚合DEPOSIT市值后用Python计算标准分档，避免与模型SQL复用同一分档实现。上界外客户不进入分母；同一客户多条持有先求和。不同账户标准答案按经理M0001、机构B001、区域EAST独立计算。

**这是3个场景的一次小样本比较，不能外推为整体准确率或稳定性保证。**同一模型仍可能产生不同SQL；工具的收益是生成期间拿到可执行校验器的反馈，代价是额外模型调用和延迟。最终执行前的权限校验没有放宽。

## 失败发现与修复记录

1. 早期随机数据缺少大额上界外客户，模型增加“上界以上”分组也可能碰巧返回相同人数。加入精确上界/上界+0.01/高额客户及一客多持有后，才能验证范围分母是否正确；早期5/5不能当作最终通过率。
2. 加边界后第一轮关闭工具仅1/3通过，开启工具虽然3/3实际SQL结果正确，但两个存款结果带数值排序维度，前端拿到的是热力图描述，整体也仅1/3通过。已修复为显式PIE可使用与排序号一一对应的唯一文字标签，保留原表所有列，独立二维分类仍拒绝合并。
3. 修复后重跑最终同版本对照得到上述2/3与3/3结果。保留[修复前关闭工具](v1.3-reports/control-before-chart-fix/results.json)、[修复前开启工具](v1.3-reports/tools-before-chart-fix/results.json)，没有将图表失败改标为成功。
4. 并发提交旧测试曾在任务SUCCESS刚提交而兼容历史尚未写入时偶发读到0行，已改成有界等待历史副作用，再验证只有1条，不放宽并发/去重断言。

[真实工具校验轨迹](v1.3-reports/tool-validation-traces.json)包含最终两轮评测的12条工具响应，其中2次静态检查失败后模型据反馈改写。仅保存工具名、轮数、SQL与结构化校验反馈，不保存思考、密钥、完整schema或原始模型响应。
