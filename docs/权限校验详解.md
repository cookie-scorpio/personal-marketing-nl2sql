# 权限校验详解（proveDataSources 全流程）

本文是 [SqlAstValidator设计说明](SqlAstValidator设计说明.md) 第 7 节的展开版，从"依据从哪来"到"每一行代码在做什么"完整走一遍权限校验。所有代码引用以当前实现为准，JSqlParser 细节见 [JSqlParser数据结构速查](JSqlParser数据结构速查.md)。

## 1. 一句话模型与责任边界

权限校验回答的唯一问题：**对任何一个可能的数据库状态，这条查询能返回的每一行，是否都落在当前调用者被授权的范围内？**

- 它是**静态证明**：不执行 SQL、不看数据，只依据 SQL 结构推导。任何依赖"当前数据恰好如何"的论证都不成立；
- 它是 **fail-closed**：证明不出来就拒绝，不存在默认放行；
- 它**不定义权限**：权限的"依据"全部来自服务端输入（见第 2 节），校验器只是把"这些依据确实约束住了每张表"变成一个可判定的图推导问题；
- 对象级兜底不在它身上：执行账号 `nl2sql_app` 只有业务库权限，`mysql.user` 等在数据库层就不可达。

## 2. 依据从哪里来（信任根）

校验器构造参数 `(user, parameters, confirmedCustomers, maxRows)` 中的前三个就是全部依据：

| 依据 | 来源 | 进入证明的方式 |
|---|---|---|
| 账号数据范围 | JWT 登录态 → `CurrentUser` → `DataScopePolicy.scopeOf(user)`（角色→范围列/值的**服务端写死映射**） | 种子 `ValueFact(范围值)`；账号模式的获证判据 |
| 已确认客户 | 会话流程：单客来自用户在界面上确认的 `resolvedCustomerId`；@名单来自服务端逐个核验过范围的 `customerIdsJson` | 种子 `identityFacts` 里的 `ValueFact(编号)` |
| 命名参数表 | 服务端规划时写入（`DataScopePolicy.condition` 注入范围值、解析出的客户 ID） | `factOf` 把 `:name` 解析成 `ValueFact(参数值)` |
| 对象白名单 | `SCHEMA`/`FUNCTIONS` 常量 | 列解析与函数校验的前置 |

关键不变量：**模型产出的 SQL 文本不是依据**。模型写的 `manager_id='M0002'` 会被解析成事实并参与传播，但种子永远是服务端注入的值——连通不到种子的事实无法让数据源获证。

调用方接线（谁在什么时机用什么种子）：

| 调用方 | user | confirmedCustomers | 模式 |
|---|---|---|---|
| `SqlSafetyValidator.validate` | null | null | 纯安全（`proveDataSources` 直接返回） |
| `GeneratedSqlScopeValidator.validate` | 登录用户 | null | 账号模式 |
| `validateCustomer` | null | 单个编号 | 客户模式 |
| `validateCustomers` | null | 编号集合 | 批量模式 |
| `SqlPlanningTools.validate_sql` | 登录用户 | 可能的单个编号 | 混合模式 |

`QueryTaskProcessor.acceptPlan` 对每条新 SQL 的调用顺序：`safety.validate` → 按任务是否解析出客户走 `validateCustomer`/`validateCustomers`。

## 3. 参与证明的数据结构

```java
private sealed interface Fact permits ColumnFact, ValueFact { }
private record ColumnFact(Binding binding, String column) implements Fact { }  // 某数据源的某列
private record ValueFact(String value) implements Fact { }                     // 一个具体取值
private record Edge(Fact from, Fact to) { }                                    // 有向边：from 的事实可流向 to
```

- 事实只有两种：**列事实**和**取值事实**。等值条件 `a = b` 在两个事实之间连边，含义是"b 的取值被约束时，a 同样被约束"（沿 from→to 方向传播）；
- `Binding`：一个数据源绑定，携带两个证明标记 `scopeProven`（账号模式已获证）与 `customerProven`（客户模式已获证）。物理表两个标记初始 false；CTE 引用/派生表初始 true（内部块已证明过）；
- `Scope.windowNames/aliases/bindings`：作用域，`parent` 指向外层块——关联子查询的一切跨块行为都靠这条链；
- `Run.customerListProven`：IN 名单证明的收集处（约束收集阶段写入，证明阶段消费）。

### 3.1 Scope 与 Binding：名字目录、数据源条目、证明落点

**Scope = 一个查询块的"名字目录"**，四个字段：`bindings`（别名 → 数据源条目，FROM/JOIN 登记）、`parent`（外层查询块的作用域，顶层为 null）、`aliases`（本块输出列别名，GROUP BY/HAVING/ORDER BY 可引用）、`windowNames`（本块 WINDOW 子句定义的命名窗口）。每个查询块一个 Scope——外层一条、CTE 体一条、派生表一条、UNION 每个分支一条、每个表达式子查询一条，`parent` 串成 SQL 的作用域嵌套链。

**Binding = 目录里的一个条目**：`baseTable`（物理表名，null 表示 CTE/派生表）、`columns`（允许引用的列：物理表为白名单列，派生表为内部块输出列）、`scopeProven/customerProven`（两个证明标记——**权限证明的最终落点就是这两个布尔值**）、`id`（报错文案定位用）。两种形态：physical（物理表，标记初始 false，等待证明）与 derived（CTE/派生表，标记初始 true，内部块已证明但列不作外块种子）。同一物理表出现两个别名 = 两个独立 Binding，各自证明。

**权限校验什么时候需要看 outer 的 Scope**：唯一读取点是两条证明链开头的 `outerBindings(scope)`——沿 parent 收齐外层绑定，把已获证的播种为本块种子。生效需要四个条件同时成立：①当前块是**表达式里的子查询**（FROM 派生表/CTE 体传 outer=null，不支持 LATERAL）；②外层存在已获证绑定；③内层 WHERE 有跨块等值（把内外 Binding 的列事实连成边）；④内层自己的表无法独立获证。方向性：事实只能从外层流向内层（外层证明先于内层运行）。`parent` 链的另一个读者是 `resolveColumn`（关联列解析），它决定了跨块边能否建立；`aliases/windowNames` 则不向外层查找（每块自己的）。

### 3.2 对象关系图与生命周期

```
Run（一次 validate 的共享状态：节点预算/来源编号/IN名单收集）
 └─ validate → analyzeSelect ─┬─ declareCtes ──────→ analyzeSelect（CTE 体，outer=null）
                              ├─ analyzeSetOperation ─→ analyzeSelect（每个分支）
                              └─ analyzePlainSelect（每个查询块）
                                   ├─ new Scope(outer)                    ① 名字目录
                                   ├─ bindDataSources ─→ Binding 放入 bindings  ② 数据源条目
                                   ├─ validateWindowDefinitions → windowNames
                                   ├─ collectConstraints ─→ Edge(Fact→Fact)      ③ 证明素材
                                   │      └─ factOf/resolveColumn → ColumnFact(Binding, 列) ← 引用②
                                   ├─ proveAccountScope / proveCustomerBinding         ④ 两条证明链
                                   │      └─ outerBindings(scope)：沿 parent 收外层 Binding 播种
                                   ├─ checkExpression ─（遇子查询）→ analyzeSelect（内层块）
                                   └─ judgeDataSources：逐 Binding 检查标记 → 403104/403105
```

| 结构 | 生命周期 | 创建者 | 读者 | 写者 |
|---|---|---|---|---|
| `Run` | 一次 validate | `validate()` | 所有阶段 | 各阶段 |
| `Scope` | 一个查询块 | `analyzePlainSelect` | `resolveColumn`、`outerBindings`、`checkOrderBy` | 绑定/别名/窗口名登记 |
| `Binding` | 一个 FROM 项 | `bindDataSource` | 两条证明链、`resolveColumn`、`judgeDataSources` | 两条证明链（标记翻转） |
| `Fact`/`Edge` | 一个查询块的证明 | `collectConstraints`/`factOf` | `propagate`、两个标记函数 | 约束收集阶段 |
| `ExprEnv` | 一次表达式校验调用 | `analyzePlainSelect`/`checkOrderBy` | `checkExpression` 及子处理 | — |

## 4. 阶段一：约束收集 `collectConstraints`

**触发时机**：`analyzePlainSelect` 在绑定数据源之后、授权证明之前调用两次——一次传 WHERE，一次传每个 JOIN 的 ON（LEFT JOIN 额外传 `nullableSide` = 右表绑定）。

```java
private void collectConstraints(Expression condition, Scope scope, List<Edge> edges,
                                Binding nullableSide, Run run)
```

逐分支语义：

| 输入形态 | 处理 | 理由 |
|---|---|---|
| `null` | 直接返回 | 子句没写 |
| `ParenthesedExpressionList` 且 size==1 | 解开括号递归 | `(a = b)` 只是加了括号的等值 |
| `AndExpression` | 左右两个子条件各自递归 | AND 的每一半都无条件成立，事实可以合流 |
| `InExpression` | 转 `collectInListProof` | 名单证明的特殊入口（见第 5 节） |
| `EqualsTo` | 两侧经 `factOf` 变事实，连边 | 等值是唯一"双向保证"的关系 |
| 其它（`>`、`LIKE`、函数…） | 什么都不做 | 不是等值，不构成约束事实 |
| `OrExpression` | **不递归** | 见下方正确性说明 |

等值连边时区分两种情形：

- `nullableSide == null`（WHERE 或 INNER JOIN 的 ON）：**双向**两条边。行集满足 `a = b`，两侧事实互相蕴含；
- `nullableSide` 非 null（LEFT JOIN 的 ON）：只有当一端恰好属于右表绑定时，加一条**指向右表**的边。依据：左连接中右表出现在结果里的行必然满足 ON（不满足的被丢弃、以 NULL 补位），所以 ON 只约束右表；左表的行无论 ON 真假全部保留，ON 约束不到左表。

三个语义规则由此天然成立：

1. **OR 不出边**：返回的每一行只满足 `A ∨ B` 中的至少一个分支，不保证满足哪一个——任何单个分支的事实都不能推广到全部返回行。.sound 的替代表达是改写成 UNION（每个分支被独立证明），集合运算对"行集受约束"封闭；
2. **函数/算术一侧不出边**：`c.manager_id = CONCAT(...)` 的右侧取值无法静态核对，`factOf` 返回 null，整条不出边；
3. **范围条件写在 LEFT JOIN 的 ON 里约束不到左表**：`dim_customer c LEFT JOIN fct_transaction t ON c.manager_id='M0001' AND ...` 中，范围条件一侧不是 t 的列 → 不出边 → c 无事实可达 → 403104。

## 5. 阶段二：IN 名单证明 `collectInListProof`

批量名单模式的契约（提示词原话："生成的SQL必须使用 customer_id IN (上述全部编号)……不得增删或替换编号"）在这里变成可证明的约束。七个守卫按序检查，**任一不满足即保持沉默**（不报错，授权交由本块其余约束）：

1. `confirmedCustomers != null`——非客户模式没有"确认名单"可核对；
2. 左侧是 `Column`；
3. 列名是 `customer_id`；
4. 列带表限定（才能定位到具体数据源）；
5. 限定名在本块绑定表中存在；
6. `collectStringLiterals` 成功——右侧列表**每个元素都是字符串字面量**；出现数字、命名参数、子查询整体放弃（部分收集会产生假证明）；
7. 字面量非空且 `confirmedCustomers.containsAll(literals)`——整体落在服务端核验名单内。

全部通过后 `run.customerListProven.add(ColumnFact(绑定, customer_id))`——该数据源的 customer_id 获得与"等值连通到确认客户"同等级别的事实。注意收集发生在**约束阶段**（证明之前），这就是修复旧版"IN 证明晚于证明、永不生效"缺陷的关键。

## 6. 阶段三：授权证明——调度器与两条证明链

权限证明拆成两条**相互独立**的链：账号链（`proveAccountScope`）只读写 `scopeFacts/allowed/scopeProven`，客户链（`proveCustomerBinding`）只读写 `identityFacts/bound/customerProven`——两条链共享的只有只读的等值边表与绑定清单，因此先后运行与交织运行收敛到同一结果。`proveDataSources` 是调度器，最后统一判定。

### 6.0 调度器 proveDataSources

```java
boolean accountMode = user != null;
boolean customerMode = confirmedCustomers != null;
if (!accountMode && !customerMode) return;   // 纯只读安全校验，无身份要求
DataScopePolicy.Scope account = accountMode ? DataScopePolicy.scopeOf(user) : null;
if (accountMode) proveAccountScope(scope, edges, account);   // 标记 scopeProven
if (customerMode) proveCustomerBinding(scope, edges, run);   // 标记 customerProven
judgeDataSources(scope, account, customerMode);              // 统一判定
```

混合模式（两者同时开启）下两条链先后各跑一遍，判定合并执行——保持既有报错顺序：逐绑定先 403104 后 403105。

### 6.1 账号链 proveAccountScope

种子与外层播种：

```java
if (account.value() == null || account.value().isBlank())
    fail(ACCOUNT_SCOPE_INVALID, "账号数据范围未配置");       // 纵深防御（scopeOf 已先行校验）
scopeFacts.add(new ValueFact(account.value()));              // 种子：账号范围值
for (Binding outerBinding : outerBindings(scope))
    if (outerBinding.scopeProven) {                          // 外层播种（关联子查询）
        scopeFacts.add(new ColumnFact(outerBinding, account.column()));
        allowed.add(new ColumnFact(outerBinding, CUSTOMER_ID));
        allowed.add(new ColumnFact(outerBinding, CAMPAIGN_ID));
    }
```

不动点循环每轮：沿边传播 `scopeFacts` 与 `allowed`，然后对每个物理绑定尝试标记（非物理绑定跳过；已获证的跳过）：

| 数据源 | 获证条件（满足其一） | 获证后 |
|---|---|---|
| `dim_customer` | `scopeFacts` 含其**范围列**（branch_id/manager_id/region_code 之一）；或 `allowed` 含其 customer_id | `scopeProven=true`；`allowed += 其 customer_id`（成为新的授权来源） |
| 其余物理表 | `allowed` 含其关键列（营销活动表 campaign_id、其余 customer_id） | `scopeProven=true`；`fct_customer_marketing` 额外 `allowed += campaign_id` |

### 6.2 客户链 proveCustomerBinding

种子与外层播种：

```java
for (String customer : confirmedCustomers) identityFacts.add(new ValueFact(customer));
identityFacts.addAll(run.customerListProven);               // IN 名单证明（第 5 节）
for (Binding outerBinding : outerBindings(scope))
    if (outerBinding.customerProven)
        bound.add(new ColumnFact(outerBinding, CUSTOMER_ID));
```

不动点循环每轮：沿边传播 `identityFacts` 与 `bound`，然后对每个物理绑定尝试标记：

| 数据源 | 获证条件（满足其一） | 获证后 |
|---|---|---|
| `dim_customer` | `identityFacts` 或 `bound` 含其 customer_id | `customerProven=true`；`bound += 其 customer_id`（成为新的绑定来源） |
| 其余物理表 | `identityFacts` 或 `bound` 含其关键列 | `customerProven=true`；`fct_customer_marketing` 额外 `bound += campaign_id` |

两条链的不动点循环结构相同：**事实集合只增不减（有界）、绑定标记只翻转一次 → 必然终止**；每轮沿边传播后尝试标记，标记新增的事实让下一轮继续推给相连数据源（dim_customer 获证 → 事实表靠连接获证的联动机制）；链式级联能否在一轮内完成取决于边序，外层 while 保证无论边序如何都收敛。表达式与条件的**递归深度**另有 200 层硬上界（`Run.expressionDepth`）——StackOverflowError 是 Error 而非 Exception，`catch (Exception)` 接不住，必须在到达之前拦截，因此对抗性长链/深嵌套在打爆线程栈之前被干净拒绝。

```java
for (Map.Entry<String, Binding> entry : scope.bindings.entrySet()) { ... }
```

逐绑定检查（保持既有顺序：每个绑定先 403104 后 403105）：

- 账号模式下未获证 → 403104。文案是给修复 SQL 的模型看的：写明账号要求的条件、别名与来源编号（`数据源 dim_customer（别名 c，来源编号 3）`），并预告两条易踩的坑（CTE 授权不传递、OR/NOT 不作依据）；
- 客户模式下未获证 → 403105。

## 7. `resolveColumn` 在证明中的角色

`factOf` 遇到列就调 `resolveColumn`，它返回的 `ColumnFact(binding, column)` 把列钉到具体数据源上：

- **带限定**（`t.customer_id`）：沿作用域链找别名，**命中即检查列存在**，不存在直接 422104、不向外层继续——与 SQL 解析语义一致；
- **不带限定**：逐层统计含此列的绑定数，多于一个即"字段含义不明确"（逼迫 SQL 写清来源，证明图才无歧义），恰有一个即成功，零个继续向外层（合法关联引用）；
- 带库名前缀（`db.t.col`）→ 403102。

列存在性检查在证明**之前**发生（约束收集阶段就调 `resolveColumn`），所以白名单是证明的前提：不存在的列根本进不了证明。

## 8. 完整跟踪 A：账号模式（proveAccountScope）+ LEFT JOIN

客户经理账号（范围列 `manager_id`，值 `M0001`）：

```sql
SELECT c.customer_id, t.amount_cny
FROM dim_customer c
LEFT JOIN fct_transaction t ON t.customer_id = c.customer_id
WHERE c.manager_id = 'M0001' AND t.transaction_date >= '2026-01-01'
LIMIT 100
```

**约束收集**：

| 条件 | 结果 |
|---|---|
| `c.manager_id = 'M0001'`（WHERE，nullableSide=null） | 双向边：`ColumnFact(c,manager_id) ↔ ValueFact(M0001)` |
| `t.transaction_date >= '2026-01-01'`（Greater，非等值） | 不出边 |
| `t.customer_id = c.customer_id`（LEFT JOIN ON，nullableSide=t） | 单向边：`ColumnFact(c,customer_id) → ColumnFact(t,customer_id)` |

**证明（proveAccountScope，账号链逐轮状态；identityFacts/bound 属于客户链，本例不运行）**：

| 轮次 | scopeFacts | allowed | 标记动作 |
|---|---|---|---|
| 种子 | {ValueFact(M0001)} | ∅ | — |
| 1 传播 | + ColumnFact(c,manager_id) | ∅ | — |
| 1 标记 | | | **c 获证**（范围列命中）；allowed += ColumnFact(c,customer_id) |
| 2 传播 | 不变 | + ColumnFact(t,customer_id)（沿 ON 单向边） | — |
| 2 标记 | | | **t 获证**（allowed 含其 customer_id） |
| 3 | 无任何新增 → 收敛 | | |

**判定**：c、t 均已获证 → 通过。

**变体一**：WHERE 改为 `c.branch_id='B001'`（团队负责人的列，但当前账号是客户经理）——传播后 `scopeFacts` 获得 `ColumnFact(c,branch_id)`，而获证判据检查的是范围列 `manager_id` → 永不命中 → 403104；
**变体二**：把范围条件移进 LEFT JOIN 的 ON——该等值右侧不是 t 的列 → 不出边 → c 无事实可达 → 403104。

## 9. 完整跟踪 B：批量名单（proveCustomerBinding）+ 营销链

`validateCustomers(sql, Map.of(), ["C00000001","C00000002"])`（user=null）：

```sql
SELECT m.campaign_name FROM fct_customer_marketing f
JOIN dim_marketing_campaign m ON m.campaign_id = f.campaign_id
WHERE f.customer_id IN ('C00000001','C00000002')
LIMIT 10
```

| 阶段 | 发生什么 |
|---|---|
| 约束收集 | JOIN ON（INNER，双向边）：`f.campaign_id ↔ m.campaign_id`；IN 条件走 `collectInListProof`：七个守卫全过（列限定 f、全部字符串字面量、⊆ 确认名单）→ `customerListProven += ColumnFact(f, customer_id)` |
| 播种 | `identityFacts = {ValueFact(C00000001), ValueFact(C00000002), ColumnFact(f,customer_id)}`；`scopeFacts/allowed/bound` 为空 |
| 第 1 轮标记 | f：关键列 customer_id，`identityFacts` 含 `ColumnFact(f,customer_id)` → **f 获证**；f 是 `fct_customer_marketing` → `bound += ColumnFact(f,campaign_id)` |
| 第 2 轮 | 传播：`bound` 沿 ON 边到达 `ColumnFact(m,campaign_id)` → m：关键列 campaign_id，`bound` 命中 → **m 获证** |
| 收敛后判定 | 全部获证 → 通过 |

变体：IN 名单混入 `C99999999`（不在确认名单）→ 守卫 7 失败 → 无证明 → 403105；IN 写成 `('C00000001', 123)` → 守卫 6 失败（非字符串字面量）→ 同样拒绝。

## 10. 跨块传播：关联子查询

```sql
SELECT c.customer_id,
       (SELECT COUNT(*) FROM fct_transaction t WHERE t.customer_id = c.customer_id) AS txn_count
FROM dim_customer c WHERE c.manager_id = 'M0001' LIMIT 10
```

时序是关键：外层块的 `proveDataSources` **先于**表达式校验运行（表达式校验才会递归进入子查询）。因此内层块证明时：

1. `outerBindings(scope)` 找到外层 `c`，其 `scopeProven=true`；
2. 播种：`allowed += ColumnFact(c, customer_id)`；
3. 内层边 `t.customer_id ↔ c.customer_id`（`resolveColumn` 沿 parent 链解析到外层列）；
4. 传播 → `allowed` 获得事实 `ColumnFact(t,customer_id)` → t 获证。

如果外层没获证（例如 WHERE 是 `c.branch_id='B001'`），外层在判定处先行 403104，根本走不到子查询。**方向性**：事实只能从外层流向内层；反向（子查询的约束救外层）不成立——`outerBindings` 只收集 `scope.parent` 链，且外层证明先运行。更多传播形态见第 14 节例集。

## 11. 正确性论证

1. **AND 链的事实无条件成立**：`WHERE (A AND B)` 的每一行同时满足 A 与 B，因此两个分支的等值事实对全部返回行成立；
2. **LEFT JOIN 方向性与 NULL 扩展语义一致**：右表出现在结果的行必然满足 ON；左表全部出现；
3. **集合运算封闭性**：UNION（受限集的并）、INTERSECT（交）、EXCEPT（差）的结果仍受限——逐分支证明后集合层无需再证；
4. **OR 不出边**：返回行只保证满足一个析取支；把不同析取支的事实混入同一图会导致 `manager_id='M0001' OR manager_id='M0002'` 被误证。sound 的表达是改写 UNION（每分支独立证明）；
5. **CTE/派生表预证明但不作本块种子**：内部块的证明使用同一份依据，预证明安全；"不作种子"是刻意保守——把范围条件埋进派生表再外连事实表，与埋进 OR 同罪；
6. **fail-closed**：兜底分支拒绝未知表达式类型、`resolveColumn` 拒绝未知列、判定拒绝一切未获证绑定——不存在默认放行；
7. **终止性**：事实集合单调递增且有界、标记单次翻转。
8. **聚合函数无特权**：`SUM`/`COUNT`/`MAX` 只是表达式，证明的对象是**数据源**——子查询里哪怕只 `COUNT(*)`，其表绑定也必须独立获证。实测：无约束聚合子查询、统计无权客户的标量子查询、`IN` 两人、`OR` 两人、以及"全表总数 − 我的总数"的差值追踪攻击全部 403104；被放行的聚合输入集都是可见集的子集，其上的任何算术仍只涉及可见数据，统计推断（tracker query）被封闭。

## 12. 报错对照与排查

| 错误码 | 触发点 | 常见原因 |
|---|---|---|
| 403104 | 判定：账号模式下存在未获证绑定 | 忘写范围条件；范围列写错（branch_id vs manager_id）；条件写在 LEFT JOIN 的 ON 里；条件在 OR 分支里；条件埋在派生表里 |
| 403105 | 判定：客户模式下存在未获证绑定 | IN 名单越界/夹带非字符串；事实表未与确认客户连接 |
| 403103 | `scopeOf` 返回空值 | 账号配置缺失（运营问题） |
| 403106 | `scopeOf`：质量管理员 | 该角色无业务查询权 |
| 422104 | `resolveColumn`：列不在白名单 | 列名拼错或引用了敏感原始列 |

## 13. 已知行为边界

- **事实表直连确认客户即可获证**（`t.customer_id = :resolvedCustomerId` 不必挂 dim_customer）——与"限定为已确认客户"的契约语义等价；
- **客户模式不校验账号范围、账号模式不校验客户绑定**，两者独立开关，混合模式下都要求；
- **`proveDataSources` 在每个 PlainSelect 上恰好运行一次**：CTE 体、派生表、UNION 分支、表达式子查询各自递归进入 `analyzeSelect` → `analyzePlainSelect`，无一处遗漏也无一处重复计数（同一物理表在不同块出现是不同绑定、分别证明）。

## 14. 传播走查：分支级例集

本节用六个由浅入深的 SQL，把证明过程**走到分支级**：每个函数走了哪个 if、为什么走、没走的分支为什么没走（以"未走"标注）。记号约定：`CF(绑定, 列)` = ColumnFact，`VF(值)` = ValueFact。六个例子按分支覆盖互补设计，14.7 的矩阵给出总覆盖图。

### 14.1 例 1：账号模式 · 三表连接 · LEFT JOIN 方向性 · 命名参数种子

```sql
SELECT c.customer_id, h.product_name, t.amount_cny
FROM dim_customer c
JOIN fct_product_holding h ON h.customer_id = c.customer_id
LEFT JOIN fct_transaction t
       ON t.customer_id = h.customer_id AND t.transaction_date >= '2026-01-01'
WHERE c.manager_id = :scopeManagerId AND c.age > 18
LIMIT 10
```

调用：`validate(sql, manager)`（客户经理，范围列 `manager_id`，范围值 `M0001`），参数表 `{scopeManagerId: "M0001"}`。

**阶段 A：绑定（bindDataSources）**

| 步骤 | 走到的分支 |
|---|---|
| `c` | Table 分支 → 无库名限定 → 非派生表 → SCHEMA 命中 → `Binding.physical`，两标记 false |
| `h` | 同上（fct_product_holding 命中白名单） |
| `t` | 同上 |
| JOIN 检查 | h：RIGHT/FULL/NATURAL/CROSS/SIMPLE/APPLY/SEMI 全 false、无 USING → 通过；t：isLeft=true → 通过，后续 ON 收集传 nullableSide=t |
| WINDOW 检查 | getWindowDefinitions()==null → `validateWindowDefinitions` 直接返回 |

**阶段 B：约束收集（collectConstraints）**

| # | 输入 | 走到的分支 | 产出 |
|---|---|---|---|
| 1 | WHERE = AndExpression | AndExpression 递归分支 | 拆为两个子条件，nullableSide=null 一路下传 |
| 2 | `c.manager_id = :scopeManagerId` | EqualsTo 分支 | 左：factOf 走 Column 分支 → resolveColumn（带限定、最内层命中、列在白名单）→ `CF(c,manager_id)`；右：factOf 走 JdbcNamedParameter 分支且参数表命中 → `VF(M0001)`；nullableSide=null → 双向两条边 |
| 3 | `c.age > 18` | 非 EqualsTo 出口（GreaterThan） | 未走：不出边——factOf 未被调用，`c.age` 与 `18` 此时都不是事实 |
| 4 | INNER JOIN 的 ON：`h.customer_id = c.customer_id`（nullableSide=null） | EqualsTo 分支 | 左 `CF(h,customer_id)`、右 `CF(c,customer_id)` → **双向两条边**（INNER 的等值互相蕴含） |
| 5 | LEFT JOIN 的 ON = AndExpression（nullableSide=t） | AndExpression 递归分支（nullableSide 下传） | 拆两个子条件 |
| 6 | `t.customer_id = h.customer_id` | EqualsTo 分支 | 左 `CF(t,customer_id)`、右 `CF(h,customer_id)`；第一个 if（右端==nullableSide）不走；第二个 if（左端==nullableSide）走 → 单向边 `CF(h,customer_id)→CF(t,customer_id)` |
| 7 | `t.transaction_date >= '2026-01-01'` | 非 EqualsTo 出口（GreaterThanEquals） | 未走：不出边。对照：若写成 `=`，左端 CF(t,txn_date) 是 nullableSide → 会走"右→左"分支产生 `VF→CF(t,txn_date)` 的边（字面量也能流向右表），只是本例没有授权意义 |

未走分支汇总：括号解包（无括号条件）、InExpression（无 IN）、factOf 的 StringValue 分支（等值右侧没有裸字符串字面量）、factOf 返回 null 的三个子形态（无函数侧、无数字侧、无缺失参数）。

**阶段 C：证明（proveAccountScope，账号模式）**

账号链种子：`scopeFacts={VF(M0001)}`、`allowed=∅`。外层播种：`scope.parent==null` → 无。客户链不运行（confirmedCustomers=null）。

| 轮 | propagate 命中的边 | 集合增量 | 标记走到的分支 |
|---|---|---|---|
| 1 | scopeFacts 轮：边 `VF(M0001)→CF(c,manager_id)` 命中；反向边的目的端已在集合 | scopeFacts += CF(c,manager_id) | c → proveAccountScope 的 **dim_customer 规则·第一析取**（scopeFacts 含范围列）命中（第二析取因 `\|\|` 短路未求值）；scopeProven=true；allowed += CF(c,customer_id)。h、t → proveAccountScope 的 **依赖表规则**：allowed 空 → 落空。客户链本例未运行（confirmedCustomers=null） |
| 2 | allowed 轮：边 `CF(c,customer_id)→CF(h,customer_id)`（INNER ON 的边）命中；**同一次扫描内**边 `CF(h,customer_id)→CF(t,customer_id)`（LEFT JOIN 单向边）接续命中——级联：扫描中新增的事实让其后的边继续生效 | allowed += CF(h,customer_id)、CF(t,customer_id) | h、t → proveAccountScope 的依赖表规则命中 → 双双 scopeProven=true |
| 3 | 账号链两个集合传播均无新增；标记无翻转 | — | while(changed) 退出 |

轮次归属依赖边在列表中的收集顺序（本例 INNER ON 的边先于 LEFT ON 的边，两跳在同一轮内级联完成）；若边序相反，t 的获证会推迟一轮——**不动点结果相同**，外层 while 保证无论边序如何都收敛。

**判定**：三个绑定 scopeProven 均 true；`confirmedCustomers==null` → 403105 检查整段跳过 → **通过**。

**阶段 D：表达式校验（证明通过后才走）**

SELECT 项：Column → checkColumn（带限定 → resolveColumn 命中）；WHERE 的 And/EqualsTo/GreaterThan → BinaryExpression 白名单命中；`:scopeManagerId` → 字面量组直接放行（**表达式层不核对参数表**——参数有效性是证明层的职责，见例 2f）；LIMIT 10 → LongValue 且范围内。

**变体**：

- 无 WHERE：`collectConstraints(null)` 走 null 出口 → 零条边 → 判定 403104（收集阶段空转也是一条分支）；
- 自连接触发 proveAccountScope 的 dim_customer 规则·**第二析取**：`FROM dim_customer c JOIN dim_customer d ON d.customer_id=c.customer_id WHERE c.manager_id='M0001'` —— 轮 1 c 经第一析取获证；轮 2 allowed 传播到 `CF(d,customer_id)`；标记 d 时第一析取（scopeFacts 含 d 的范围列）不命中、第二析取（allowed 含其 customer_id）命中 → d 获证。

### 14.2 例 2：客户模式 · 三种事实来源 · 七个守卫 · 数字不是事实

调用：`validateCustomers(sql, {resolvedCustomerId:"C00000001"}, ["C00000001","C00000002"])`。

**例 2a（通过）**：

```sql
SELECT t.amount_cny FROM fct_transaction t
WHERE t.customer_id = :resolvedCustomerId
  AND t.customer_id IN ('C00000001')
  AND (t.branch_id = 'X' OR t.branch_id = 'Y')
LIMIT 10
```

约束收集（WHERE 是三层 AndExpression 树）：

| # | 输入 | 走到的分支 | 产出 |
|---|---|---|---|
| 1 | `t.customer_id = :resolvedCustomerId` | EqualsTo 分支 | 左 CF(t,customer_id)；右走 factOf 命名参数分支（参数表命中）→ VF(C00000001)；双向两条边 |
| 2 | `t.customer_id IN ('C00000001')` | InExpression 分支 → collectInListProof | 七个守卫全过（客户模式开、左侧是列、列名 customer_id、带表限定、限定名命中绑定、列表全字符串字面量、⊆ 确认名单）→ customerListProven += CF(t,customer_id) |
| 3 | `(t.branch_id='X' OR t.branch_id='Y')` | **括号解包分支**（ParenthesedExpressionList size==1，内含一个 OrExpression）→ 解包后走**非 EqualsTo 出口** | 未走：OR 里的两个等值都不出边——OR 让它们失去"对全部返回行成立"的资格；连 collectInListProof 都不会被调用（OrExpression 在 InExpression 检查之前就从非等值出口返回） |

证明（proveCustomerBinding，纯客户模式）：种子 identityFacts = {VF(C00000001)} ∪ customerListProven；轮 1 传播：边 `VF(C00000001)→CF(t,customer_id)` 命中；标记：t → proveCustomerBinding 的**依赖表规则**（identityFacts 含关键列）→ customerProven=true。判定：账号链未运行（user==null）→ 403104 检查跳过；customerProven ✓ → **通过**。

未走分支：账号链未运行（user==null）；本例也没有 dim_customer（其规则属于两条链各自的部分）。

**五个拒绝变体（每个触发不同守卫/分支）**：

| 变体 | 走到的分支 | 结果 |
|---|---|---|
| 2b：等值删掉，IN 改 `('C00000001','C99999999')` | collectInListProof **守卫 7**（containsAll 失败）→ 沉默 | identityFacts 里只有两个 VF 种子、无边可达 t → 403105 |
| 2c：IN 改 `('C00000001', 123)` | collectStringLiterals 遇 LongValue 返回 false → **守卫 6** | 数字字面量在客户编号域里连事实都不是（factOf 同样没有数字分支）→ 403105 |
| 2d：IN 左侧改 `t.branch_id` / 去掉表限定 | **守卫 3** / **守卫 4** | 沉默 → 403105 |
| 2e：等值改 `t.customer_id = 123` | factOf 走**兜底 null 出口**（LongValue 不在 factOf 的任何分支里） | 无边 → 403105 |
| 2f：等值改 `t.customer_id = :foo`（参数表无 foo） | 表达式层：JdbcNamedParameter 在**字面量组**放行（表达式层不查参数表）；证明层：factOf 的 containsKey 判 false → null → 无边 | **形态合法与依据有效分层校验** → 403105 |

### 14.3 例 3：关联子查询——跨块传播与 resolveColumn 全分支

**例 3a（通过）**：

```sql
SELECT c.customer_id,
       (SELECT COUNT(*) FROM fct_transaction t WHERE t.customer_id = c.customer_id) AS txn_count
FROM dim_customer c
WHERE c.manager_id = :scopeManagerId LIMIT 10
```

1. 外层块证明先行：c 获证（路径同例 1）；
2. 表达式阶段：SELECT 项 [1] = ParenthesedSelect → **checkExpression 的子查询分支** → `analyzeSelect(子查询, outer=env.scope(), ...)`——相互递归点，`env.scope()` 使内层 `Scope.parent` 指向外层；
3. 内层绑定 t 后收集 WHERE 等值：factOf 左 → resolveColumn 限定 `t` **内层命中** → CF(t,customer_id)；factOf 右 → resolveColumn 限定 `c`：**内层作用域未命中 → 沿 parent 命中外层** → **CF(外层c,customer_id)**（携带的是外层 Binding 对象——跨块传播的物理载体）；双向两条边；
4. 内层 proveAccountScope：`outerBindings(scope)` 找到外层 c 且 scopeProven=true → **外层播种**：allowed += CF(c,customer_id) → 传播沿边到 CF(t,customer_id) → t 获证 → 内层判定通过；
5. 内层表达式：`COUNT(*)` → checkFunction 白名单命中 + **AllColumns 豁免分支**（仅 count 下豁免）。

**resolveColumn 其余分支用一行变体覆盖**：

| 变体 | 走到的分支 | 结果 |
|---|---|---|
| 子查询写 `z.customer_id`（z 不存在） | 限定名全链未命中 → 兜底 fail | 422104 |
| 子查询写 `t.unknown_col` | 限定命中但列不在白名单 → fail | 422104 |
| 内层连接两张表后写不带限定的 `customer_id` | **非限定歧义分支**（matches.size()>1） | 422104——逼迫写限定名，证明图才无歧义 |
| 内层写不带限定、仅外层才有的 `open_date` | **非限定内层零命中 → 沿 parent 命中外层** 分支 | 合法的关联引用 |

**例 3b（拒绝 · 方向性）**：

```sql
SELECT d.customer_id FROM dim_customer d
WHERE EXISTS (SELECT 1 FROM dim_customer x
              WHERE x.manager_id='M0001' AND x.customer_id=d.customer_id) LIMIT 10
```

WHERE 根是 ExistsExpression → collectConstraints 走**非等值出口**（EXISTS 不出边）→ 外层证明：d 无事实 → **403104，且内层从未被递归**（证明先于表达式校验）。语义上这条 SQL 安全（返回的就是 M0001 名下客户），这是保守性的真实代价；改写为外层 JOIN 即通过。

### 14.4 例 4：批量名单 + 营销链联动 + 内层 bound 播种

**例 4a（通过）**：

```sql
SELECT m.campaign_name FROM fct_customer_marketing f
JOIN dim_marketing_campaign m ON m.campaign_id = f.campaign_id
WHERE f.customer_id IN ('C00000001','C00000002') LIMIT 10
```

1. IN 名单：守卫全过 → customerListProven += CF(f,customer_id)；
2. 播种：identityFacts = {VF(C00000001), VF(C00000002), CF(f,customer_id)}；
3. 轮 1 标记：f → proveCustomerBinding 的**依赖表规则·keyColumn 走 customer_id 分支**（f 不是营销活动表）→ identityFacts 命中 → customerProven=true；**fcm 联动分支**：baseTable==fct_customer_marketing → bound += CF(f,campaign_id)；
4. 轮 2：bound 沿 ON 边传播 → CF(m,campaign_id)；标记：m → 依赖表规则 keyColumn **走 CAMPAIGN_ID 分支**（dim_marketing_campaign 没有 customer_id）→ bound 命中 → m 获证；
5. 判定：账号链未运行（user==null）→ 403104 检查跳过；customerProven ✓ → 通过。

**例 4b（拒绝 · 营销活动表单独出现）**：`SELECT m.campaign_name FROM dim_marketing_campaign m WHERE m.campaign_status_code='ACTIVE'` —— 批量模式下 key=campaign_id 无法连通 → **403105**（注意：不是 403104——账号检查因 user==null 被跳过，错误码随模式而变）。

**例 4c（通过 · 内层 bound 播种）**：在 4a 基础上加 `AND EXISTS (SELECT 1 FROM fct_transaction t WHERE t.customer_id = f.customer_id)`——内层证明时 `outerBindings` 找到 f 且 customerProven=true → **bound += CF(f,customer_id)** → 传播到内层 t → t 获证。与例 3 对照：那里走的是 allowed（账号模式），这里走 bound（客户模式）——外层播种按当前模式选择集合。

### 14.5 例 5：混合模式——两条链独立判定

`SqlPlanningTools` 场景：user=客户经理 且 confirmedCustomers={C00000001}，参数表含 resolvedCustomerId：

```sql
SELECT t.amount_cny FROM dim_customer c JOIN fct_transaction t ON t.customer_id=c.customer_id
WHERE c.manager_id='M0001' AND c.customer_id=:resolvedCustomerId LIMIT 10
```

两条链先后各自运行（同一个结构的不动点循环）：

| 轮 | 账号链 | 客户链 | 标记 |
|---|---|---|---|
| 账号链轮 1 | scopeFacts += CF(c,manager_id) | — | c：dim_customer 规则·第一析取命中 → scopeProven=true；allowed += c.customer_id |
| 账号链轮 2 | allowed += CF(t,customer_id) | — | t：依赖表规则命中 → scopeProven=true |
| 客户链轮 1 | identityFacts += CF(c,customer_id) | — | c：dim_customer 规则命中 → customerProven=true；bound += c.customer_id |
| 客户链轮 2 | bound += CF(t,customer_id) | — | t：依赖表规则命中 → customerProven=true |
| 收敛 | 两条链无新增 | | |

判定循环按绑定插入序（c 先 t 后）逐个检查、每个绑定先 403104 后 403105：通过。两个变体：去掉客户等值 → c 的 customerProven=false → **403105**（账号检查已过，错误码来自客户检查）；去掉范围条件 → c 的 scopeProven=false → **403104**（先于 403105 触发——同一绑定的两个检查有先后顺序）。

### 14.6 例 6：CTE 预证明不做种子 + UNION 分支独立

**例 6a（拒绝）**：

```sql
WITH scoped AS (SELECT customer_id FROM dim_customer WHERE manager_id='M0001')
SELECT t.amount_cny FROM scoped s JOIN fct_transaction t ON t.customer_id = s.customer_id LIMIT 10
```

- `scoped` 的绑定走 **derived 分支**：内部块递归校验通过 → `Binding.derived` 预置 scopeProven=customerProven=true；
- 两条链的标记循环轮到 s 时都走 **`!binding.isPhysical() → continue` 分支**（每轮都跳过）；t：allowed/identityFacts 永远不含其 customer_id（s 的列不作种子——刻意保守：埋进 CTE 的范围条件与埋进 OR 同罪）；
- 判定：s 通过（预证明），t → 403104 → 整体拒绝。

**例 6b（通过）**：外层再 `JOIN dim_customer c ON c.customer_id=t.customer_id WHERE c.manager_id='M0001'`——c 获证 → allowed 传给 t → t 获证；s 全程预证明。改写要点：**范围约束必须出现在"使用数据源的那个块"里**。

**例 6c（UNION 分支独立）**：`分支1(有约束) UNION ALL 分支2(无约束)`——`analyzeSetOperation` 逐分支 `analyzeSelect`：分支 1 证明通过并返回列；分支 2 在**它自己的** `analyzePlainSelect` → 判定处抛 403104，异常直接上抛（分支 1 已完成的工作作废，无缓存）。集合层本身不运行证明——它没有数据源。
