# 个金营销 NL2SQL 平台 v1.2 实施说明与接口数据字典

本文按 v1.0 文档的“版本范围—运行配置—处理流程—数据库—API—未实现项—验收—许可”结构记录 v1.2 的实际实现。v1.0、v1.1 文档保留历史记录；升级、接口调用和当前能力以本文及代码为准。所有姓名、手机号占位值、资产和交易均为虚构演示数据。

## 1. 版本范围

平台面向个人金融营销查询：业务人员用自然语言描述问题，系统确认查询对象和统计条件，生成受控 MySQL SQL，返回指标、图表、明细及简要分析。

技术栈保持 JDK 17、Spring Boot 4.1.1、MyBatis-Plus 3.5.16、Maven 3.9.16、Vue 3、TypeScript、Element Plus 2.x、ECharts 6、MySQL 8.4、Redis 7.x。SQL AST 使用现有依赖带入的 JSqlParser 5.2。当前本地 Redis 是单节点；保留 Redis Cluster 配置。Milvus、BCG-E3 仍只保留外置接口，不连接向量服务。后续查询统一使用 MySQL，不使用 Spark SQL 或 Hive。

### 1.1 本版已实现

| 需求 | 实现与边界 |
|---|---|
| 连续对话界面 | 用户靠右、助手靠左；发送立即清空输入；查询说明、阶段、澄清、确认、错误、图表均放在对应消息中 |
| 流式状态 | SSE 发送真实阶段和完整任务快照；先显示“当前查询内容为：…”；不伪造打字效果、工具调用或模型思考正文 |
| 停止与错误 | 运行时发送按钮变为停止；取消、超时、模型失败等在助手消息中保留；沿用实际 JDBC 中断和终态保护 |
| 思考开关 | 默认开启，每次提交固定设置；同任务的澄清、确认、响应重试、SQL 修复沿用该设置；规则查询仍可直接完成 |
| 客户身份澄清 | “李先生”不能作为完整姓名直接执行资产查询；先在当前权限范围定位、补充、选择客户，再检查时间等条件 |
| 虚构完整姓名与脱敏 | 数据库新增完整姓名；候选客户在后端脱敏；业务 SQL 禁止读取完整姓名列；结果组装再次处理标准姓名、手机字段 |
| 多轮上下文 | 支持已确认客户的“他的产品持有”、常见时间替换和分组调整；显式新客户编号/姓名不继承旧客户 |
| 持久化 | MySQL 保存会话、用户/助手消息、最后可用上下文及阶段事件；刷新或重新登录可以打开会话继续操作 |
| 提交幂等 | 同用户、同幂等键、同内容返回同一任务；不同内容返回冲突；Redis 加速、MySQL 唯一约束保证最终去重 |
| 并发保护 | 会话行锁、任务当前读、版本条件更新、问题编号和确认令牌一起保证只推进一次；同会话只能有一个未结束任务 |
| 复杂 SQL | 受控非递归 CTE、派生表、关联子查询、UNION/UNION ALL、窗口函数、分组及 INNER/LEFT JOIN；逐查询块验证列和数据范围 |
| 可视化增强 | 六类图形实际渲染，多指标分图；增加按类别比较的多系列时间折线，修正客户标识常量干扰图表判断的问题 |
| SQL 文件日志 | 独立 UTF-8 滚动日志记录时间戳、任务/请求编号、生成 SQL、脱敏参数、校验与执行结果，便于核查首次、修复和降级 SQL |

继承 v1.1 的登录、JWT、三级数据范围、术语读取、规则与 DeepSeek 混合解析、缺失/矛盾澄清、高风险确认、最多两次 SQL 修复、受控模板降级、查询历史、操作审计等功能。

### 1.2 设计取舍与客户澄清建议

核心顺序为“确定对象—核对适用条件—形成查询计划”。规则快速路径也必须经过身份校验，不能只要出现资产、交易等关键词就忽略人名或额外条件。思考开关只影响模型调用方式，不替代身份确认、权限和 SQL 校验，也不保证 SQL 一定正确。

以“帮我查找一下李先生的资产信息”为例：

1. 将“李先生”识别为不完整客户称谓，在当前用户授权范围内查询候选，不查询资产。
2. 没有候选时仅提示“当前可查询范围内未找到”，不透露权限外是否存在该客户。
3. 超过 10 名候选时不返回截断列表让用户误选，要求补充客户编号、虚构完整姓名或手机号后四位。
4. 1–10 名候选时展示编号、脱敏姓名、机构和脱敏手机，要求明确选择；完整姓名唯一匹配也不直接自动执行。
5. 选择编号后重新验证候选关系和权限，将 `customer_id` 保存到任务。生成、修复、确认恢复的每条业务 SQL 都必须保留该客户约束。
6. 当前资产/当前持有属于快照查询，不因为缺少时间机械反问。交易发生时间、开户时间、历史资产等仍按问题逐项澄清；数据库不具备的历史能力不能编造。

避免同类问题的具体措施：

| 风险 | 当前处理 |
|---|---|
| 将称谓当作完整姓名 | 先做客户定位；未确认时阻止后续业务 SQL |
| 同名客户选错 | 展示脱敏候选并由用户选择，服务端验证选择合法性 |
| 身份补充后丢失原问题 | 定位补充与原业务问题分别处理；确认后替换称谓，保留业务主题 |
| 追问误用上一个客户 | 只有追问且没有显式新身份才继承；显式编号/姓名重新定位 |
| 模型删掉客户或权限条件 | AST 分别证明账号范围和已选客户限制，修复 SQL 也必须验证 |
| 失败/取消覆盖上下文 | 只在 SUCCESS 或确有数据可用的模板降级后更新；正常空结果仍属于完成的查询 |
| 模板擅自放宽条件 | 个人资产/持有模板只完整匹配少量明确表达；额外条件进入模型；已定位单客不使用通用群体降级模板 |

姓名识别采用当前演示数据适用的中文姓名/称谓规则，并非通用实体识别模型。复杂称谓、多个人同时比较、企业名称、别名关系不保证自动解决，需提供客户编号或重新完整描述。本版没有将每个时间、指标、筛选条件都规范化成独立结构化槽位；复杂追问由带明确前后关系的文本交给模型理解，仍可能需要反问。

### 1.3 前端设计约定

使用 frontend-design 技能，具体约定见 [v1.2界面设计约定](development/v1.2界面设计约定.md)。沿用近白底、细边框、中行红主操作色、Element Plus 图标及系统中文字体。连续消息为主体，底部固定输入区，顶部提供完整会话和新建会话入口。

Enter 发送，Shift+Enter 换行；输入法组合输入不提交。运行中的思考开关不可修改。网络导致提交结果不确定时，保留原幂等键与原问题重试；明确被服务端拒绝则将问题放回输入框。新建/切换会话会断开当前进度订阅，但不会自动取消后台任务；可从会话历史返回继续处理。新会话不继承旧上下文。

左侧侧栏统一提供“新建会话”和“会话历史”，按最近更新时间分为今天、昨天和更早，支持分页加载、刷新、错误重试和当前会话标记。长标题省略显示并提供完整提示；列表独立滚动。窄屏通过菜单打开，选中会话后收起。主区域不再提供历史抽屉或“查询记录”页签，旧查询历史API仅保留兼容，不再由当前页面调用。

示例问题采用等宽两列按钮，560px以下为单列；文字按按钮实际宽度自然换行。新建尚未发送问题的会话只重置前端状态，不写入数据库、不增加历史条目。加载会话、提交未确认或取消请求进行中时禁止切换，避免操作相互覆盖。

空数据库首次启动没有会话历史；已有数据库重启后仍保留用户会话。V5会回填旧任务，因此开发测试记录也可能出现在列表中。启动时不会自动清空数据，维护清理必须先确认范围并备份，不能根据标题或用户编号批量误删。2026-08-28经用户确认，本机已按固定编号清单清理166个旧演示/验收会话；清理期间新建的2个用户会话保留。详见[本机会话清理记录](development/2026-08-28会话清理记录.md)。

### 2.2 模型、思考与查询配置

自由问题需配置 `MODEL_PROVIDER=deepseek`、`DEEPSEEK_BASE_URL`、`DEEPSEEK_API_KEY`、`DEEPSEEK_MODEL`。默认模型标识沿用 `deepseek-v4-flash`，地址可为服务根地址或完整 `/chat/completions` 地址。密钥只在后端配置，不传给前端或写入日志。

| 配置 | 环境变量 | 默认值 | 说明 |
|---|---|---|---|
| app.model.provider | MODEL_PROVIDER | mock | mock 只支持规则能力，超范围明确报错 |
| app.model.deepseek.thinking-enabled | DEEPSEEK_THINKING_ENABLED | true | 适配器缺省设置；对话 API 省略 thinking_enabled 时固定按 true 接收 |
| app.model.deepseek.max-tokens | DEEPSEEK_MAX_TOKENS | 16384 | 首次最终 JSON 与思考输出的总额度 |
| app.model.deepseek.retry-max-tokens | DEEPSEEK_RETRY_MAX_TOKENS | 32768 | 空内容或截断时仅一次响应重试的额度 |
| app.model.deepseek.read-timeout-seconds | DEEPSEEK_READ_TIMEOUT_SECONDS | 120 | 模型读取超时，与 SQL 执行超时分开 |
| app.query.execution-timeout-seconds | QUERY_EXECUTION_TIMEOUT_SECONDS | 60 | 单次 SQL 的 JDBC 超时 |
| app.query.max-result-rows | QUERY_MAX_RESULT_ROWS | 100 | SQL 外层 LIMIT 允许值与返回上限；生成器默认仍用不超过100 |
| app.query.max-clarification-rounds | QUERY_MAX_CLARIFICATION_ROUNDS | 5 | 同一任务可完成的澄清轮数 |
| app.query.sql-log-dir | SQL_REVIEW_LOG_DIR | logs | 相对于后端进程工作目录，建议部署时用绝对路径 |

已有 `application-local.yml` 若显式写了 v1.1 的 `thinking-enabled: false`、4096/8192 token 或 60 秒模型超时，旧值仍覆盖默认配置。请按需要更新这些非敏感项；页面选择会覆盖该次任务的思考开关，但不改变 token 和超时配置。

模式启用通过模型接口 `thinking.type=enabled/disabled` 显式传递。思考正文不会进入 SQL 候选、消息、SSE 或日志；只使用最终 JSON 规划。原始模型调用未改成 token 流式 API，SSE 流式传送的是平台真实执行阶段。规则路径无模型调用，开启开关也不会强制调用模型。

协议参考：[DeepSeek Chat Completions](https://api-docs.deepseek.com/api/create-chat-completion/)、[Thinking Mode](https://api-docs.deepseek.com/guides/thinking_mode/)。本版验证了请求协议和开关传递，不把这一验证表述成真实模型准确率测试。

### 2.3 Redis、持久化和部署

会话、消息、上下文、任务、事件均以 MySQL 为准。Redis 只缓存提交键到任务编号的映射，缓存 TTL 为24小时；Redis 不可用时仍由 MySQL 去重，不使用仅进程内锁作为跨实例保护。历史 `SessionContextStore` 不再承担新会话的上下文存储。

Redis Cluster 示例见 `crm/backend/src/main/resources/application-redis-cluster.example.yml`。幂等缓存键形如 `nl2sql:submit:{用户编号}:SHA256(提交键)`，使用单键读写，不依赖跨槽事务。本地验收是单节点 Redis，未进行真实 Cluster 故障切换测试。

部署时执行 `mvn package` 生成 `crm/backend/target/nl2sql-crm-backend-1.2.0.jar`，前端 `npm run build` 生成 `dist/`。静态服务器将 `/api`、`/actuator/health` 代理至后端。SSE 代理应关闭响应缓冲/缓存，读取超时大于55秒，例如 Nginx：

```nginx
location /api/ {
    proxy_pass http://backend:8080;
    proxy_http_version 1.1;
    proxy_buffering off;
    proxy_cache off;
    proxy_read_timeout 75s;
}
```

为 SQL 日志目录提供写入权限和持久卷；多个实例应分别写文件，再由日志收集工具汇总，不能共享同一个滚动文件。V5 修改表结构并生成虚构姓名，升级前备份模拟库；回退应用前需评估协议与字段兼容性，不能直接删除迁移记录。

### 2.4 提示词与 SQL 核查日志

`crm/backend/src/main/resources/prompts/nl2sql-system.txt` 规定意图、澄清、MySQL 计划、权限和图表建议；`nl2sql-schema.txt` 提供可用字段及业务含义。完整姓名不加入模型可查询字段。`Nl2SqlPrompts` 再拼入当前日期、启用术语和当前身份范围。修改后重新构建/启动，不支持在线编辑。

默认日志为 `crm/backend/logs/sql-review.log`（从后端目录启动时）。每行由带时区的毫秒时间戳和 JSON 对象组成；SQL 内换行以 JSON 转义保留，避免一条 SQL 被误当成多条记录。日志不截断 SQL；请求编号、任务编号可关联任务和审计。

```text
2026-08-28T09:40:00.123+08:00 {"task_id":"示例任务编号","request_id":"示例请求编号","source":"RULE","phase":"GENERATED","sql":"SELECT c.customer_id FROM dim_customer c WHERE c.manager_id=:scopeManager LIMIT 100","parameters":{"scopeManager":"M0001"},"outcome":null}
```

该行仅为格式示例。实际 SQL 以真实日志为准，执行前后可能各有一行；同任务还可能有多次生成记录。

| JSON 字段/阶段 | 含义 |
|---|---|
| task_id / request_id | 对应任务和触发该动作的请求编号 |
| source | RULE、DEEPSEEK、TEMPLATE_FALLBACK 等计划来源 |
| sql | 本次业务查询的完整 SQL，模板保留命名参数 |
| parameters | 命名绑定参数；password、secret、token、mobile、phone、customerName 类键值替换为 [REDACTED] |
| GENERATED | 首次、修复或模板生成的待校验 SQL |
| REJECTED | 校验拒绝，outcome 是业务错误码或校验分类 |
| EXECUTING | 即将交给 JDBC 的 SQL |
| EXECUTED | JDBC 已返回，outcome 包含返回行数 |
| SQL_ERROR | SQL 错误分类，不直接记录数据库原始错误正文 |
| TIMED_OUT / CANCELLED | 执行阶段观察到超时/取消；未进入 SQL 执行时不保证产生这一类日志 |

SQL 核查日志记录业务查询计划，不记录登录 SQL、候选定位 SQL、完整 Prompt、模型思考或 JWT。未生成业务 SQL 的澄清消息没有 SQL 日志；被取消的迟到模型返回不会继续成为执行计划。日志用于排查，不是与 MySQL 事务原子提交的审计账本。

单文件20MB，按日期/大小压缩滚动，保留14天、总量上限1GB。保留清理由滚动策略触发，不是独立的按时删除任务。日志仍可能包含 SQL 字面量和客户编号，仅限授权人员读取，不用于真实客户数据。

按任务编号筛选：

```powershell
Select-String -LiteralPath .\crm\backend\logs\sql-review.log -SimpleMatch '待核查task_id'
```

## 3. 处理流程与关键实现

### 3.1 对话与状态

```text
提交问题 + Idempotency-Key + thinking_enabled
  → 查询/锁定会话、检查幂等和活动任务
  → 同事务写任务、用户消息、助手快照和事件
  → 提交成功后异步认领任务
  → 确认客户身份 → 理解条件/意图 → 必要时澄清
  → 规则模板或模型 SQL → AST/权限/客户约束 → 必要时风险确认
  → MySQL执行 → 脱敏、指标、多图、分析
  → 终态、消息和上下文提交 → SSE发送已提交事件
```

运行阶段有 RECEIVED、INTENT_ANALYZING、SQL_GENERATING、VALIDATING、EXECUTING、REPAIRING、FALLING_BACK、PACKAGING；ASKING 和 CONFIRMING 等待用户；SUCCESS、FAILED、CANCELLED、TIMED_OUT、DEGRADED 为终态。`progress` 是阶段进度，不是模型思考比例或数据库完成百分比。

前端使用 fetch 读取 SSE，以便携带 Bearer JWT 和 `Last-Event-ID`。服务器每约350毫秒读取持久化事件，约10.5秒发送心跳，单次连接最长55秒；等待用户/终态时关闭。客户端按事件编号和任务版本去重，断线后重新订阅；连续连接异常时用状态接口恢复进度。关闭浏览器或 SSE 不等于取消查询。

每一轮澄清保留一条助手消息，该轮各阶段更新其 payload；事件表另存阶段快照。最终消息保留结果/错误。刷新后从消息快照恢复当前状态；页面内“执行阶段”列表来自本次订阅收到的阶段，不保证刷新后重建所有历史阶段列表，完整事件可按任务回放。

### 3.2 幂等、并发与取消

幂等摘要是 `session_id`、去除两端空白后的 `query_text`、`preferred_display`（缺省 AUTO）、`thinking_enabled`（缺省 true）组成的稳定 SHA-256 摘要。`X-Request-ID` 不参与摘要。数据库唯一键 `(user_id,idempotency_key)` 是最终依据，Redis 命中仍核对用户、键与摘要。数据库未自动清理任务，所以去重生命周期不只24小时，任务存在时仍有效。

提交事务使用 READ COMMITTED；同会话先取得会话行写锁，再检查活动任务。为避免 INSERT IGNORE 的锁升级死锁，会话创建采用 INSERT … ON DUPLICATE KEY UPDATE。MyBatis 本地缓存采用 STATEMENT，避免加锁后复用旧的空结果。澄清、确认、取消先锁会话，再对任务 FOR UPDATE 当前读，不复用等待锁前的 REPEATABLE READ 快照。

后台认领和每次阶段推进使用 `state_version` 条件更新；CAS 未成功即停止。状态、助手消息与 SSE 事件在同一个 MySQL 事务内提交。澄清消费对应 question_id，确认消费对应 confirm_token；重复/过期操作返回409，不再次执行。不同会话可并行；同会话的 ASKING、CONFIRMING 也占用活动任务位置。

取消接口重复调用可返回相同终态；已成功的任务不会被改成取消。执行器约200毫秒检查持久化状态，设置 JDBC `setQueryTimeout`、`setMaxRows` 并调用 `Statement.cancel`。取消返回表示不再推进，MySQL 中断有短暂传播时间。正在进行的模型 HTTP 调用不保证立刻断开，但返回结果会被丢弃，不继续 SQL/修复/降级。

消息和上下文持久化不代表工作进程崩溃后自动续跑。崩溃遗留的活动任务可在恢复服务后取消，再新提问。本版不实现持久化作业队列和自动重新调度。

### 3.3 SQL AST、安全与修复

JSqlParser 5.2 将 SQL 解析为语法树，限制单条 SELECT、长度30000字符、解析超时2秒、查询嵌套深度12及节点数量。外层必须有常量 LIMIT，默认1–100；子查询内部 LIMIT 不代替外层限制。标识符采用英文名称/别名，不接受跨库引用。

业务物理表白名单为 `dim_customer`、`fct_transaction`、`fct_product_holding`、`dim_marketing_campaign`、`fct_customer_marketing`。每张表有明确列清单，`customer_name` 完整姓名列不在自由 SQL 清单中；改别名、包函数、放到子查询也不能绕过。禁止星号投影（COUNT(*)除外）、写操作、锁定查询、注释、多语句、变量及未知函数。

| 支持 | 限制 |
|---|---|
| 非递归 CTE | CTE 内部独立验证；不能遮蔽业务表；输出列在SELECT内声明，不支持递归及CTE列名列表 |
| 派生表 | 必须有别名，内部先独立满足授权要求 |
| 关联标量/EXISTS/IN 子查询 | 校验内层对象、列，并证明其与已授权外层的关联 |
| UNION、UNION ALL | 每个分支单独验证，列数一致，整体返回上限明确 |
| INNER JOIN、LEFT JOIN | 使用明确 ON；不支持逗号/CROSS/RIGHT/FULL/NATURAL/USING JOIN |
| 聚合、CASE、常用函数、窗口函数 | 函数白名单；窗口使用内联 OVER；不支持命名窗口、DISTINCT ON、SQL_CALC_FOUND_ROWS等扩展 |

权限不再通过“某处出现了范围字符串”判定。校验器只从必定成立的 AND 等值条件提取证明，OR/NOT 内出现的限制不算授权依据。LEFT JOIN 的 ON 只能约束可空右表，不能拿右侧条件证明左表受限。客户的账号范围通过 customer_id 关联传递给事实表，营销关联再传递给活动；每个物理数据源都必须被证明受限。单客任务还要单独证明已选客户限制，不能拿经理编号冒充客户限制。

示例（结构示例，当前用户为 EAST 负责人）：

```sql
WITH scoped AS (
  SELECT c.customer_id, c.total_asset_amount
  FROM dim_customer c
  WHERE c.region_code = 'EAST'
)
SELECT scoped.customer_id,
       ROW_NUMBER() OVER (ORDER BY scoped.total_asset_amount DESC) AS asset_rank
FROM scoped
LIMIT 10
```

验证遵循无法证明就拒绝，不承诺 MySQL 全语法兼容。例如把已授权 CTE 投影列再连接到新的事实表，当前没有完整列血缘传播，可能被保守拒绝，需改写为各查询块独立受限的 SQL。AST 验证不能证明业务口径正确，也不能预测扫描成本。风险评估仍沿用可解释规则，没有 EXPLAIN 成本预算。

初始安全校验失败直接结束，不通过修复放宽权限。仅已知 MySQL 表达错误进入最多两次修复；连接故障、权限错误、取消、超时不修复。每次修复/降级重新校验，新的风险计划需重新确认。无合适模板时 `fallback.data_available=false`，不返回替代口径数据。参考 [JSqlParser usage](https://jsqlparser.github.io/JSqlParser/usage.html)。

### 3.4 图表与分析

v1.1 代码已经包含 BAR、LINE、AREA、PIE、SCATTER、HEATMAP，不能将用户当时只观察到柱图/表格理解成代码完全没有其他图形。是否生成取决于 SQL 返回形态、字段元数据和模型建议。本版加强选择规则与连续对话中的完整渲染。

| 数据形态 | 展示原则 |
|---|---|
| 单行/单项指标 | 指标卡与明细，不强行绘图 |
| 一个分类、多项指标 | 不同指标分图，保持各自单位 |
| 时间维度 | 按时间排序折线；明确 AREA 建议且非负可用面积图 |
| 时间加分类维度 | 每个指标生成一张多系列折线，按分类对比；缺失点保留为空，不补零 |
| 少量分类、非负可加总指标 | 柱图；性别/渠道等适合构成时可补充饼图 |
| 两个数值 | 合适时散点图，编号不当数值指标 |
| 两个分类维度 | 维度组合唯一时生成热力图 |
| 重复维度、超过两个维度、无法解释的形态 | 保留指标、分析和明细，不自行聚合 |
| 指定 TABLE 或无数据 | 不生成图表 |

模型提供展示类型和字段角色建议，不能直接提交任意 ECharts 配置。后端按实际数据校验并生成 ChartSpec；一张或多张图都只消费本次结果。单客结果中的常量客户编号、姓名、快照日期不应阻止其他业务维度绘图，明细仍保留这些字段。

均值/比率不能直接求和；有可靠 customer_count/contact_count 权重时加权，否则标明返回分组均值。负数、全零、比率、均值不生成构成图。所有分析只针对最多返回的有限结果，不冒充全库统计、跨组去重、趋势预测或营销因果判断。

### 4.15 数据关系与迁移

业务编号关系沿用v1.1：交易、产品持有关联客户；营销触达关联客户及活动；客户关联经理。会话按user_id隔离，一个会话包含多个任务，一个任务包含用户/助手消息和阶段事件。全部关系当前仍无物理外键，应用事务和生成器维持一致性。

V1创建11张业务/平台表，V2初始化术语，V3扩展查询计划，V4增加版本/修复/图表字段，V5增加完整虚构姓名、任务幂等/上下文字段及3张会话相关表。当前共14张业务/平台表，另有Flyway自己的flyway_schema_history技术表。

V5只为历史session_id中唯一归属一个user_id的任务回填会话和原始USER消息；不回填臆测的历史助手过程和上下文。历史共有session_id若属于多个用户，不建立共享会话。历史任务和query_history原表不删除。

数据库默认utf8mb4_0900_ai_ci；幂等键单独使用ASCII二进制排序规则以区分大小写。新会话表毫秒时间用于展示和排序，不作为并发控制依据；并发依赖锁、唯一键和版本。

## 5. API 详细示例与数据字典

### 5.1 通用约定

默认根地址 `http://127.0.0.1:8080`，本机验收用18080。JSON使用 snake_case，空的可选对象字段通常省略。除登录和健康检查外要求 `Authorization: Bearer <access_token>`；身份只从 JWT 获取，客户端不得指定可覆盖权限的用户/机构编号。`X-Request-ID` 可选。版本仍使用 `/api/v1` 路径，应用版本是1.2.0。

除SSE外，成功返回 HTTP200 和统一封装：

```json
{"code":0,"message":"处理成功","data":{},"request_id":"请求编号"}
```

提交必须提供 `Idempotency-Key`。澄清/确认不依赖该头去重，而是消费当前问题编号/确认令牌。完整机器可读契约见 [OpenAPI](../contracts/openapi/crm-nl2sql-mvp-v1.yaml)。

| POST | /api/v1/auth/login | 登录 |

### 5.2 登录与当前用户

`POST /api/v1/auth/login`：username必填≤64字符、password必填≤128字符。

```json
{"username":"director01","password":"Demo@123"}
```

响应的data结构示例：

```json
{"access_token":"JWT字符串","token_type":"Bearer","expires_in":28800,"user":{"user_id":3,"username":"director01","display_name":"演示负责人","role":"ORG_MANAGER","region_code":"EAST","branch_id":"B001"}}
```

`GET /api/v1/auth/me` 无请求体，data为同样的user结构。role为 CUSTOMER_MANAGER、TEAM_LEAD、ORG_MANAGER；manager_id、branch_id 依角色可空。登录失败/令牌失效为401001。

### 5.3 提交问题

`POST /api/v1/queries`，请求头示例 `Idempotency-Key: 50b06f3a-43fa-42db-9e20-1ead78015a49`。

| 请求字段 | 类型 | 必填/默认 | 说明 |
|---|---|---|---|
| session_id | string | 必填 | ≤36字符，建议UUID；新编号首次提交时创建会话 |
| query_text | string | 必填 | 非空，≤1000字符；提交时去两端空白 |
| preferred_display | string | AUTO | 兼容保留；参与幂等摘要，实际展示仍由模型/后端结果判断 |
| thinking_enabled | boolean | true | 本任务固定思考设置 |
| Idempotency-Key（头） | string | 必填 | 8–128个ASCII字母/数字或 `._:-`，区分大小写 |

```json
{"session_id":"11111111-1111-4111-8111-111111111111","query_text":"统计近30天各机构客户交易金额","preferred_display":"AUTO","thinking_enabled":true}
```

响应data：

```json
{"task_id":"22222222-2222-4222-8222-222222222222","session_id":"11111111-1111-4111-8111-111111111111","status":"RECEIVED","progress":0,"status_url":"/api/v1/queries/22222222-2222-4222-8222-222222222222/status"}
```

重复键+相同请求返回同一task_id及其当前状态，可能已经完成；不同内容返回HTTP409/code409005。同会话有活动任务、但使用新键提交时返回409006。同键同内容即使已有活动任务仍可重放原响应。不同用户的相同键互不冲突，但不能共用对方的session_id。

### 5.5 SSE事件

`GET /api/v1/queries/{taskId}/events`，请求头携带JWT；可传 `Last-Event-ID: 123`，缺省0，从该编号之后继续。响应类型 `text/event-stream`，没有ApiResponse外层。

```text
id: 124
event: status
data: {"task_id":"22222222-2222-4222-8222-222222222222","session_id":"11111111-1111-4111-8111-111111111111","status":"EXECUTING","progress":75,"message":"正在查询已授权的营销数据","clarification_round":0,"repair_attempts":0,"execution_timeout_seconds":60,"cancellable":true,"state_version":5,"thinking_enabled":true,"display_query":"统计近30天各机构客户交易金额"}

:heartbeat

```

`event:status` 的data是完整TaskStatus，id来自全局自增event_id，单任务可能不连续。没有新事件且任务已经等待/结束时发送 `event:snapshot`，不带id，然后关闭。断开后用最后收到的id重连；不把断线、连接55秒超时或心跳当成任务失败。终态错误仍在data的status/error中；SQL未开始或失败都可能没有result。

### 5.6 回答反问、确认与取消

`POST /api/v1/conversations/{sessionId}/messages`：

```json
{"task_id":"22222222-2222-4222-8222-222222222222","question_id":"33333333-3333-4333-8333-333333333333","answer_text":"C00000001","selected_options":[]}
```

task_id、question_id必填，answer_text非空时优先，或使用selected_options。候选选择把编号放入answer_text，服务端验证它属于本轮候选且仍有权限。成功data与提交响应一致，继续订阅原任务。普通独立追问请重新POST `/queries` 并沿用session_id，不能用messages接口创建新任务。

`POST /api/v1/queries/{taskId}/confirmations`：

```json
{"confirm_token":"当前任务返回的随机令牌","decision":"CONFIRM","reason":"演示分析需要"}
```

confirm_token和decision必填，decision为CONFIRM或REJECT，reason为兼容可选字段，当前不参与权限判断。confirmation对象字段为confirm_token、risk_level(MEDIUM/HIGH)、message、reasons(string[])。确认只执行保存的计划，不重新生成SQL；REJECT调用取消。成功返回TaskStatus。令牌随状态消费，没有单独时间过期字段。

`POST /api/v1/queries/{taskId}/cancel` 无需请求体，返回TaskStatus。已终态时返回原终态；重复取消不新增业务执行。

### 5.7 完整会话与上下文

`GET /api/v1/conversations?page_no=1&page_size=30`：page_no≥1，page_size为1–100。data直接为数组，没有total；按updated_at倒序、session_id排序。前端用返回是否满页决定是否继续加载，最后一次可能返回空页。

```json
[{"session_id":"11111111-1111-4111-8111-111111111111","title":"统计近30天各机构客户交易金额","state_version":2,"created_at":"2026-08-28T09:00:00","updated_at":"2026-08-28T09:00:01"}]
```

`active_task_id` 可空，表示待处理任务；title来自首条问题前160字符，不由模型生成，不支持重命名。

`GET /api/v1/conversations/{sessionId}?before_message_id=0&page_size=100`：默认返回最近100条消息，响应内部按message_id升序；用最早message_id作为before_message_id继续获取更早一页。before≤0按最新页处理，page_size为1–100。has_more是“本页数量达到上限”的提示，不是精确总量。

data示例（payload在此简写；实际为完整TaskStatus）：

```json
{
  "session_id":"11111111-1111-4111-8111-111111111111",
  "title":"统计近30天各机构客户交易金额","state_version":2,
  "context":{"query":"统计近30天各机构客户交易金额","source_task_id":"22222222-2222-4222-8222-222222222222"},
  "messages":[
    {"message_id":101,"task_id":"22222222-2222-4222-8222-222222222222","role_code":"USER","content":"统计近30天各机构客户交易金额","created_at":"2026-08-28T09:00:00"},
    {"message_id":102,"task_id":"22222222-2222-4222-8222-222222222222","role_code":"ASSISTANT","content":"查询完成","payload":{"status":"SUCCESS"},"created_at":"2026-08-28T09:00:00"}
  ],
  "has_more":false
}
```

context字段为query、customer_id（可空）、source_task_id（可空）。它只描述最后一个可用查询的条件和已确认客户，不含查询行数据或模型思考，也不作为客户端可修改的权限来源。用户只能读取自己的会话；无此会话与他人会话均返回404001。

### 5.9 兼容查询记录、删除与健康检查

`GET /api/v1/query-history?page_no=1&page_size=20&keyword=交易`：page_no从1开始、page_size为1–100、keyword可选。data为items、total、page_no、page_size。items字段为history_id、task_id、user_id、query_text、intent_code、status_code、sql_summary、result_summary、created_at、deleted。

```json
{"items":[{"history_id":"44444444-4444-4444-8444-444444444444","task_id":"22222222-2222-4222-8222-222222222222","user_id":3,"query_text":"统计近30天各机构客户交易金额","status_code":"SUCCESS","result_summary":"查询完成","created_at":"2026-08-28T09:00:01","deleted":false}],"total":1,"page_no":1,"page_size":20}
```

`GET /actuator/health` 无需登录，正常包含 `{"status":"UP"}`；不是模型正确率或SQL质量检查。

### 7.3 运维与数据边界

- 所有客户数据仅供演示。完整虚构姓名不能被理解成允许接入真实姓名；真实数据需另行设计权限、加密、日志和模型数据出口。
- V5对旧脱敏姓名生成新的虚构名字，不是恢复真实姓名。模拟数据重置会改变结果，不要在验收或用户使用时随意执行`--reset`。
- 历史会话迁移只保留可确认所有者的原始用户问题，不伪造旧版没有保存的中间消息、阶段或上下文；旧任务结果仍在query_task中，旧查询历史API仍保留兼容，当前页面只提供完整会话入口。
- 新版消息和事件会保存结果快照，暂未自动过期；部署前评估存储占用、备份和清理策略。只读会话接口返回的已存结果不会重新执行SQL。
- 集成测试和HTTP验收会创建持久化任务与会话，今后应在独立测试库及对应后端实例执行，不要在用户正在使用的数据库中重复跑验收。此次旧记录清理是一次性维护，不是启动逻辑、定时任务或按关键词隐藏列表。
- SQL日志可能包含查询字面量和模拟客户编号，严格控制目录权限，不随仓库提交。日志落盘失败不属于事务保证；需通过部署监控检查磁盘和日志写入状态。
- LIMIT约束返回量，不等于限制扫描量；SQL超时和风险确认仍必要。SQL AST通过也不代表业务口径正确，保留SQL核查流程。
- JWT当前保存在浏览器本地存储，只适用于演示；登出后重新登录同一账号可以恢复数据库会话，其他账号不能读取。
