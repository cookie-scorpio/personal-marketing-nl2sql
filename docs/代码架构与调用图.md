# 代码架构与调用图

本文根据 v1.5 当前代码整理。项目没有训练或托管自研神经网络；运行时采用“确定性规则优先、DeepSeek 处理自由问题、可信服务端负责安全与执行”的混合架构。`llm-service/` 和 `data-product/` 当前主要是扩展位置，可运行实现集中在 `crm/backend/`。

## 2. 模型与 NL2SQL 内部架构

```mermaid
flowchart TD
    Q[用户自然语言问题]
    CTX[服务端上下文处理<br/>脱敏、连续追问合并、客户/名单范围锁定]
    MG[ModelGateway.interpret]
    RP[RuleBasedSemanticParser.parse]
    TQ{缺少明确时间口径?}
    TD{supportsDeterministicPlan?}
    SEM[SemanticQuery<br/>结构化意图与槽位]
    PROVIDER{配置的模型适配器}
    MOCK[mock<br/>仅支持已命中的规则路径]
    DS[DeepSeekModelAdapter]
    SYS[nl2sql-system.txt]
    SCHEMA[nl2sql-schema.txt]
    DYN[动态上下文<br/>业务术语、当前日期、数据覆盖、账号范围、客户范围]
    HTTP[DeepSeek Chat Completions<br/>thinking 可开关、JSON object]
    TOOL{模型请求工具?}
    GET[get_query_schema<br/>只读取结构与口径]
    VALIDATE[validate_sql<br/>SqlAstValidator 静态预检，不执行 SQL]
    JSON[DeepSeekPlan JSON<br/>intent/confidence/clarification/sql/title/display/columns]
    INTERP[QueryInterpretation<br/>规则与模型的统一输出]
    CHECK[CompletenessValidator + DisplayConflictGuard]
    ASK[ClarificationQuestion<br/>进入 ASKING]
    RULESQL[SqlPlanner<br/>模板 SQL + 命名参数 + DataScopePolicy]
    GENSQL[模型生成候选 SQL]
    UNIFIED[runPlan / acceptPlan<br/>统一安全入口]

    Q --> CTX --> MG --> RP
    RP --> TQ
    TQ -- 是 --> ASK
    TQ -- 否 --> TD
    TD -- 是 --> SEM --> INTERP
    TD -- 否 --> PROVIDER
    PROVIDER -- mock或不可用 --> MOCK
    PROVIDER -- deepseek --> DS
    SYS --> DS
    SCHEMA --> DYN --> DS
    DS --> HTTP --> TOOL
    TOOL -- get_query_schema --> GET --> HTTP
    TOOL -- validate_sql --> VALIDATE --> HTTP
    TOOL -- 不再调用工具 --> JSON --> INTERP
    INTERP --> CHECK
    CHECK -- 缺失/矛盾/展示冲突 --> ASK
    CHECK -- 规则计划完整 --> RULESQL --> UNIFIED
    CHECK -- 模型计划完整 --> GENSQL --> UNIFIED

    UNIFIED -.校验或执行可修复错误.-> FIX[ModelGateway.repair<br/>直接调用当前模型，不再走规则]
    FIX --> DS
    UNIFIED -.执行后且来源为模型.-> RR[ModelGateway.reviewResult<br/>仅传 SQL、列名、类型、行数、声明口径]
    RR --> DS
```

模型在系统里的权限边界：

- 模型可以读取允许查询的 Schema、业务术语、当前账号必须具备的数据范围，以及无客户明细的数据覆盖信息。
- 模型可以生成候选 `SELECT`、提出澄清问题、声明列角色和推荐展示方式。
- 模型工具只能做静态检查，不能执行数据库查询。
- 模型不能决定最终权限，不能绕过确认，也不能把思考正文作为 SQL 或结果使用。
- 每条模型 SQL、修复 SQL 和降级 SQL 都重新进入服务端安全及风险检查。

## 3. 一次查询的完整调用时序

```mermaid
sequenceDiagram
    autonumber
    actor User as 用户
    participant Vue as ConversationWorkspace
    participant API as api.ts
    participant Security as JWT过滤器
    participant Controller as QueryController
    participant Service as QueryApplicationService
    participant DB as MySQL/Redis
    participant Processor as QueryTaskProcessor
    participant Gateway as ModelGateway
    participant Rule as RuleBasedSemanticParser
    participant LLM as DeepSeekModelAdapter
    participant Guard as SQL安全与范围校验
    participant Executor as MySqlQueryExecutionGateway
    participant Assembler as ResultAssembler
    participant SSE as QueryEventsController

    User->>Vue: 输入问题并发送
    Vue->>API: apiRequest(POST /api/v1/queries)
    Note over Vue,API: JWT + X-Request-ID + 稳定 Idempotency-Key
    API->>Security: HTTP请求
    Security->>Controller: CurrentUser
    Controller->>Service: submit(request,user,requestId,key)
    Service->>DB: 校验幂等键、锁会话、写 query_task/message/event
    Service-->>Processor: 事务提交后 processAsync(taskId)
    Service-->>Vue: taskId + RECEIVED
    Vue->>SSE: GET /queries/{id}/events + Last-Event-ID

    Processor->>DB: RECEIVED -> INTENT_ANALYZING
    Processor->>Processor: 客户定位、名单范围、连续对话上下文处理

    alt 需要客户/时间/主题/冲突澄清
        Processor->>DB: 状态改为 ASKING并保存问题事件
        SSE-->>Vue: ASKING快照
        Vue-->>User: 展示补充条件界面
        User->>Vue: 提交答案
        Vue->>Service: POST /conversations/{id}/messages
        Service->>DB: 合并答案，ASKING -> RECEIVED
        Service-->>Processor: 重新 processAsync
    else 条件可继续
        Processor->>Gateway: interpret(question,user,active,thinking)
        Gateway->>Rule: parse + 时间检查
        alt 固定场景完整命中
            Rule-->>Gateway: SemanticQuery(source=RULE)
            Gateway-->>Processor: QueryInterpretation
            Processor->>Processor: SqlPlanner生成模板SQL和命名参数
        else 自由分析问题
            Gateway->>LLM: prompts + Schema + 术语 + 日期 + 数据范围
            loop 最多配置的工具轮数
                LLM->>Guard: validate_sql静态预检
                Guard-->>LLM: 通过或具体错误
            end
            LLM-->>Gateway: DeepSeekPlan JSON
            Gateway-->>Processor: QueryInterpretation(source=DEEPSEEK)
        end

        Processor->>DB: 状态改为 SQL_GENERATING / VALIDATING
        Processor->>Guard: 只读、AST、白名单、LIMIT校验
        opt SQL来自模型或绑定了确认客户
            Processor->>Guard: 证明账号范围、单客户或客户名单范围
        end
        Processor->>Guard: SqlRiskEvaluator.assess

        alt 需要风险确认
            Processor->>DB: 保存SQL和确认令牌，状态改为 CONFIRMING
            SSE-->>Vue: CONFIRMING + 风险原因
            Vue-->>User: 请求确认
            User->>Vue: 确认并执行
            Vue->>Service: POST /queries/{id}/confirmations
            Service->>DB: CONFIRMING -> RECEIVED，confirmed=true
            Service-->>Processor: 重新 processAsync并恢复已保存计划
        end

        Processor->>DB: 状态改为 EXECUTING
        Processor->>Executor: execute(taskId,plan,active)
        Executor->>Guard: 执行前再次安全校验
        Executor->>DB: 命名参数查询，设置超时和最大行数
        DB-->>Executor: rows
        Executor-->>Processor: 查询结果

        opt 模型生成的SQL且开启结果结构复核
            Processor->>DB: 状态改为 RESULT_REVIEWING
            Processor->>LLM: reviewResult(问题,SQL,无业务值结构摘要)
            LLM-->>Processor: aligned + reason
        end

        alt 校验/执行/结果复核出现可修复问题
            loop 整个任务最多2次
                Processor->>DB: 状态改为 REPAIRING并记录修复轨迹
                Processor->>LLM: repair(原问题,失败SQL,错误分类)
                LLM-->>Processor: 新候选SQL
                Processor->>Guard: 重新完整校验、范围证明、风险评估
            end
            opt 修复失败或达到上限
                Processor->>Processor: FallbackPlanner匹配固定模板
            end
        end

        Processor->>DB: 状态改为 PACKAGING
        Processor->>Assembler: assemble(plan,rows,source,confidence)
        Assembler-->>Processor: QueryResult
        Processor->>DB: 写结果、历史、审计、事件，状态 SUCCESS或DEGRADED
        SSE-->>Vue: 最终状态和结果
        Vue-->>User: 渲染指标、图表、表格和SQL依据
    end
```

## 4. 查询任务状态机

```mermaid
stateDiagram-v2
    [*] --> RECEIVED: 提交/补充/确认后入队
    RECEIVED --> INTENT_ANALYZING
    INTENT_ANALYZING --> ASKING: 客户、时间、主题或冲突需补充
    ASKING --> RECEIVED: 用户补充
    INTENT_ANALYZING --> SQL_GENERATING: 解释完整
    SQL_GENERATING --> VALIDATING
    VALIDATING --> CONFIRMING: 风险需确认
    CONFIRMING --> RECEIVED: 用户确认
    CONFIRMING --> CANCELLED: 用户拒绝
    VALIDATING --> EXECUTING: 无需确认或已确认
    EXECUTING --> RESULT_REVIEWING: 模型SQL开启结构复核
    EXECUTING --> PACKAGING: 规则SQL或无需复核
    RESULT_REVIEWING --> PACKAGING: 结构匹配
    VALIDATING --> REPAIRING: 可修复校验错误
    EXECUTING --> REPAIRING: 可修复数据库错误
    RESULT_REVIEWING --> REPAIRING: 结构不匹配
    REPAIRING --> VALIDATING: 生成新候选SQL
    REPAIRING --> FALLING_BACK: 无候选或达到两次上限
    FALLING_BACK --> VALIDATING: 命中固定模板
    FALLING_BACK --> DEGRADED: 没有完整模板
    PACKAGING --> SUCCESS
    PACKAGING --> DEGRADED: 返回带降级说明的结果

    RECEIVED --> CANCELLED
    INTENT_ANALYZING --> CANCELLED
    SQL_GENERATING --> CANCELLED
    VALIDATING --> CANCELLED
    EXECUTING --> CANCELLED
    RESULT_REVIEWING --> CANCELLED
    REPAIRING --> CANCELLED
    FALLING_BACK --> CANCELLED
    EXECUTING --> TIMED_OUT
    RECEIVED --> FAILED
    INTENT_ANALYZING --> FAILED
    SQL_GENERATING --> FAILED
    VALIDATING --> FAILED
    EXECUTING --> FAILED

    SUCCESS --> [*]
    DEGRADED --> [*]
    FAILED --> [*]
    CANCELLED --> [*]
    TIMED_OUT --> [*]
```

## 5. 读代码时的对应入口

| 关注点 | 主要代码 |
|---|---|
| 前端请求、JWT、幂等键 | `crm/frontend/src/app/api.ts` |

| 规则优先和模型路由 | `model/ModelGateway.java` |
| DeepSeek协议、工具调用、修复和复核 | `model/DeepSeekModelAdapter.java` |
| 提示词动态上下文 | `model/Nl2SqlPrompts.java` |

| 结果指标、图表和摘要 | `execution/application/ResultAssembler.java` |
