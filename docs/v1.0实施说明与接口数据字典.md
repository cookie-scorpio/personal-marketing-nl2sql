# 个金营销 NL2SQL 平台 v1.0 实施说明

本文记录当前代码的实际能力、配置方式、数据库结构、API 示例和后续建设建议。原始 Word 设计文档保留为参考；当其与本文或代码不一致时，以当前实现为准。

## 1. 版本范围

平台面向模拟个人金融营销数据，业务人员通过自然语言提出问题，系统完成意图识别、条件校验、反问澄清、SQL 生成、风险判断、MySQL 查询和结果分析。

本期技术栈为 JDK 17、Spring Boot 4.1.1、MyBatis-Plus 3.5.16、Maven 3.9.16、Vue 3、TypeScript、Element Plus 2.x、ECharts 6、MySQL 8.4 和 Redis 7.x。当前本地 Docker 使用单节点 Redis，另提供 Redis Cluster 配置示例。后续查询仍统一使用 MySQL，不再规划 Spark SQL 或 Hive。

### 1.1 已实现

- 数据库账号登录、JWT 会话恢复和三种轻量角色的数据范围。
- 高频明确场景优先使用规则和固定 SQL 模板，减少模型调用。
- 自由问题通过 DeepSeek V4 Flash 的 Chat Completions 兼容接口生成结构化查询计划。
- 缺少信息、条件矛盾或模型置信度低于 0.65 时主动反问。
- 从 MySQL `business_term` 表加载启用的业务术语，加入模型提示词；表结构和字段含义在适配器中明确描述。
- SQL 单语句、只读、对象白名单、结果上限存在性、危险函数与通配字段检查。
- 模型 SQL 必须包含服务端分配的数据范围条件。
- 全量请求、无过滤事实表、缺少时间限制的事实明细、复杂关联等风险需要确认。
- 确认后执行已保存的原 SQL，不再次调用模型生成新 SQL；用户不能手工编辑 SQL。
- 异步任务状态、条件补充、风险确认、结果展示、查询历史和审计记录。
- 根据结果形态生成柱状图、折线图、饼图或单项指标；明细表与分析视图可以切换。
- 指标卡汇总当前返回结果，分析区提供最高项、合计或分组均值及后续追问建议。
- Milvus 与 BCG-E3 仅保留外置接口和配置，不实际建立连接。

### 1.2 设计取舍

当前采用 Spring Boot 模块化单体，登录、任务编排、模型适配、SQL 执行和历史记录在一个进程内，以 Java 接口隔离职责。无需为演示环境额外部署 Python 模型服务或数据产品服务。

规则路径只接受固定模板可以完整回答的表达。除了识别主题，还逐项消耗已知条件与模板词；存在未识别文本、历史快照要求或模板不支持的明细/分组形式时交给模型。年龄、性别、按月趋势、同比、环比、渠道、排名、到期等扩展要求不会仅因出现“客户”或“交易金额”等关键词就套用不匹配模板。自由提问仍受当前数据库对象和 SELECT 查询能力限制，不意味着任意数据库操作。

SQL 风险评估使用可解释规则，不提供精确扫描行数或耗时预测。写入、删除、建表等非查询操作始终阻止，不属于“确认后可执行”的范围。

### 1.3 前端设计约定

- 核心任务：输入业务问题并理解返回结果。
- 层级：查询输入与当前任务状态优先，结果区按“结论—指标—图表/分析—明细—SQL依据”组织。
- 视觉：近白色底面、细边框、中行红主强调色；绿色只表达完成和可信状态，琥珀色表达风险。
- 字体：系统中文无衬线字体；标题、正文、辅助信息保持有限层级。
- 间距：以 4/8/12/16/24/32 像素为主要尺度；控件圆角约 8 像素，内容区约 10–13 像素。
- 图标：统一使用 Element Plus 图标，不混用表情符号。
- 状态：初始、运行、反问、确认、成功、空结果、失败均有明确反馈。
- 终端：常规 PC 浏览器，不以移动端作为验收目标。
- 不展示虚构的营销业绩或静态机会数字；未实现的业务入口不放入主导航。

## 2. 运行与配置

### 2.1 本地启动

1. 沿用 `deploy/local/compose.yml` 启动 MySQL 和 Redis。
2. 设置与 `deploy/local/.env` 一致的数据库、Redis 密码。
3. 启动后端。Flyway 自动应用 V1、V2、V3 迁移，不应手工修改已应用的迁移文件。
4. 如业务表没有模拟数据，按 `scripts/mock-data/README.md` 生成。
5. 启动前端，浏览器访问 `http://127.0.0.1:5173`。

```powershell
cd D:\code\boc\0824nl2sql\crm\backend
$env:JAVA_HOME = "D:\tools\jdk17" # 按本机JDK 17安装位置调整
$env:MYSQL_PASSWORD = "本地数据库密码"
$env:REDIS_PASSWORD = "本地Redis密码"
mvn test
mvn spring-boot:run
```

```powershell
cd D:\code\boc\0824nl2sql\crm\frontend
npm install
npm run dev
```

演示账号为 `manager01`、`leader01`、`director01`，密码均为 `Demo@123`。数据库只保存密码哈希。

### 2.2 DeepSeek API 填写位置

在环境变量中设置以下内容，或复制 `application-local.example.yml` 为已被 Git 忽略的 `application-local.yml` 后填写：

```powershell
$env:MODEL_PROVIDER = "deepseek"
$env:DEEPSEEK_BASE_URL = "https://api.deepseek.com"
$env:DEEPSEEK_API_KEY = "填写真实API密钥"
$env:DEEPSEEK_MODEL = "deepseek-v4-flash"
```

地址可填写服务根地址，也可填写完整 `/chat/completions` 地址。适配器使用 JSON Output，连接超时5秒、读取超时默认60秒；异常响应不会将外部正文直接暴露给页面。使用`application-local.yml`时需激活`local`配置。配置真实API后也不会改变高频规则优先策略。

在已有`app.model.deepseek`节点下可设置以下字段，与`base-url`、`api-key`、`model`同级；不配置时也使用这些默认值：

```yaml
thinking-enabled: false
max-tokens: 4096
retry-max-tokens: 8192
read-timeout-seconds: 60
```

对应环境变量为`DEEPSEEK_THINKING_ENABLED`、`DEEPSEEK_MAX_TOKENS`、`DEEPSEEK_RETRY_MAX_TOKENS`和`DEEPSEEK_READ_TIMEOUT_SECONDS`。输出上限必须为正数，重试上限不能低于首次上限。只在空最终内容、只有思考内容或`finish_reason=length`时重试一次；HTTP失败、格式错误、拒绝响应和SQL错误不自动重试。思考正文永远不作为SQL候选计划。

`MODEL_PROVIDER=mock` 时仅可使用规则支持的问法；超出范围会明确提示配置 DeepSeek，不会伪造模型结果。

协议依据：[DeepSeek Chat Completions](https://api-docs.deepseek.com/api/create-chat-completion/)、[Thinking Mode](https://api-docs.deepseek.com/guides/thinking_mode/)。官方V4默认开启思考，项目短JSON规划默认显式关闭；已完成部分真实API用例验证，不代表全部自由问句的准确率已验收。

### 2.3 Redis 与外置 RAG

当前 Redis 保存 30 分钟短期会话索引；不可用时可退回进程内缓存。集群环境可参考 `application-redis-cluster.example.yml` 配置节点和密码。该示例不创建或改造现有 Docker 集群。

`app.rag.enabled` 默认 `false`。`embedding-model`、`embedding-base-url`、`milvus-uri` 和 `collection` 只是预留配置；`EmbeddingClient`、`VectorStore` 是后续实现边界，本期不会调用它们。

### 2.4 大模型提示词的位置与职责

| 位置 | 内容 |
|---|---|
| `crm/backend/src/main/resources/prompts/nl2sql-system.txt` | 意图枚举、完备性与矛盾澄清、置信度、只读约束、JSON输出结构 |
| `crm/backend/src/main/resources/prompts/nl2sql-schema.txt` | 五张可查询表、字段释义、关联关系、金额与转化口径、数据限制 |
| `crm/backend/src/main/java/com/boc/nl2sql/model/Nl2SqlPrompts.java` | 加载固定提示词，拼入数据库术语、当前日期、账号数据范围和用户问题 |

这些提示词原先是`DeepSeekModelAdapter`里的`SYSTEM_PROMPT`和`SCHEMA_CONTEXT`常量，现已拆出为UTF-8资源文件。修改后需要重新构建/重启；当前没有在线编辑能力。规则命中的问题不会发送这些提示词到模型。

历史资产同比需要历史资产序列，当前客户画像不能提供该指标。此类问题应先解释数据限制并反问替代口径，不能把`asset_change_3m_rate`冒充同比。同一客户可能多次被触达，模型提示词要求渠道转化人数按客户编号去重。

## 3. 处理流程与关键代码

```text
自然语言问题
  → 规则识别可完整回答的高频场景
      ├─ 命中：受控语义对象 → 固定SQL模板
      └─ 未命中：DeepSeek + 表结构 + 数据库术语 → JSON查询计划
  → 完备性、矛盾、置信度检查
      └─ 需要补充：ASKING → 用户回答 → 重新识别
  → SQL只读、对象、数据范围与风险检查
      └─ 需要确认：CONFIRMING → 确认 → 执行保存的原计划
  → MySQL查询 → 指标、图表、基础分析 → 历史与审计
```

| 代码位置 | 主要职责 |
|---|---|
| `model/ModelGateway.java` | 规则与模型分流 |
| `model/DeepSeekModelAdapter.java` | API调用、思考模式与输出上限、有限重试、结构化JSON解析、低置信度反问 |
| `model/Nl2SqlPrompts.java` | 加载提示词资源，构造带数据范围的动态上下文 |
| `knowledge/BusinessTermCatalog.java` | 从MySQL加载术语定义 |
| `nl2sql/application/RuleBasedSemanticParser.java` | 高频规则、槽位、日期与矛盾识别 |
| `nl2sql/application/CompletenessValidator.java` | 完备性与矛盾校验 |
| `execution/application/SqlPlanner.java` | 固定模板和数据范围注入 |
| `execution/application/SqlSafetyValidator.java` | SQL基础静态检查 |
| `execution/application/GeneratedSqlScopeValidator.java` | 模型SQL范围检查 |
| `execution/application/SqlRiskEvaluator.java` | 可解释的风险确认规则 |
| `execution/application/ResultAssembler.java` | 指标、图表描述和分析摘要 |
| `conversation/application/QueryTaskProcessor.java` | 状态机与异步执行 |
| `features/conversation/ResultChart.vue` | 统一ECharts样式和渲染 |

状态包括 `RECEIVED`、`INTENT_ANALYZING`、`SQL_GENERATING`、`VALIDATING`、`ASKING`、`CONFIRMING`、`EXECUTING`、`PACKAGING`、`SUCCESS`、`FAILED`、`CANCELLED`。进度是业务阶段反馈，不是数据库物理执行百分比。

### 4.12 数据关系与迁移

业务关联通过编号建立：交易、产品持有、营销触达均关联客户；营销触达关联活动；客户关联经理。当前未使用物理外键，模拟数据生成器负责保持关联一致。

## 5. API 详细示例

### 5.1 通用约定

根地址默认 `http://127.0.0.1:8080`。JSON字段采用snake_case；除登录和健康检查外，均携带 `Authorization: Bearer <access_token>`。可传 `X-Request-ID`，未传时服务端生成。当前API成功返回HTTP 200，异步受理信息在响应体中表达。

```json
{"code":0,"message":"处理成功","data":{},"request_id":"请求编号"}
```

用户身份只从JWT获取，请求中不接受可覆盖权限的user_id。前端发送的Idempotency-Key目前尚未在服务端实现去重，见后续计划。

### 5.2 POST /api/v1/auth/login：登录

请求：

```json
{"username":"director01","password":"Demo@123"}
```

响应示例：

```json
{
  "code":0,"message":"处理成功","request_id":"req-login",
  "data":{
    "access_token":"JWT字符串","token_type":"Bearer","expires_in":28800,
    "user":{"user_id":3,"username":"director01","display_name":"演示负责人","role":"ORG_MANAGER","region_code":"EAST","branch_id":"B001"}
  }
}
```

用户名最大64字符、密码最大128字符。登录失败返回401001。

### 5.3 GET /api/v1/auth/me：当前用户

请求头携带Bearer Token，无请求体。响应的data与登录响应中的user结构相同，用于页面刷新后恢复身份。

### 5.4 POST /api/v1/queries：提交问题

```json
{
  "session_id":"11111111-1111-4111-8111-111111111111",
  "query_text":"统计近30天各机构客户交易金额",
  "preferred_display":"AUTO"
}
```

session_id必填，最大36字符；query_text必填，最大1000字符。preferred_display保留为兼容字段，当前由服务端依据结果自动决定展示方式。

```json
{
  "code":0,"message":"处理成功","request_id":"req-query",
  "data":{
    "task_id":"22222222-2222-4222-8222-222222222222",
    "session_id":"11111111-1111-4111-8111-111111111111",
    "status":"RECEIVED","progress":0,
    "status_url":"/api/v1/queries/22222222-2222-4222-8222-222222222222/status"
  }
}
```

### 5.5 GET /api/v1/queries/{taskId}/status：任务状态与结果

运行中返回status、progress、message等字段。等待补充时data示例：


成功时data示例（数值仅为结构示例）：

### 5.6 POST /api/v1/conversations/{sessionId}/messages：回答反问

```json
{
  "task_id":"22222222-2222-4222-8222-222222222222",
  "question_id":"33333333-3333-4333-8333-333333333333",
  "answer_text":"近30天",
  "selected_options":[]
}
```

也可只传`selected_options:["近30天"]`。answer_text非空时优先采用自由文本。task_id和question_id必填，任务必须属于当前用户且处于ASKING。成功响应与提交问题的data结构相同，随后继续轮询原task_id。

### 5.7 POST /api/v1/queries/{taskId}/confirmations：确认或取消

等待确认的状态data包含：

```json
{
  "status":"CONFIRMING","progress":65,
  "confirmation":{
    "confirm_token":"服务端生成的随机令牌","risk_level":"MEDIUM",
    "message":"该SQL可能涉及大量数据或较长查询时延，请确认后执行。",
    "reasons":["查询范围包含全部或不限范围数据"]
  }
}
```

确认请求：

```json
{"confirm_token":"服务端返回的令牌","decision":"CONFIRM","reason":"演示分析需要"}
```

取消时decision为REJECT。确认成功后返回任务状态并继续轮询；取消后为CANCELLED。令牌必须与当前任务匹配。当前令牌在状态变更后失效，尚未增加独立时间过期字段。

### 5.8 GET /api/v1/query-history：查询历史

示例路径：`/api/v1/query-history?page_no=1&page_size=20&keyword=交易`。page_no从1开始，page_size限制1–100，keyword可选。

```json
{
  "code":0,"message":"处理成功","request_id":"req-history",

    }],
    "total":1,"page_no":1,"page_size":20
  }

```

历史复用恢复原问题并重新查询，不直接执行历史SQL。

### 5.9 DELETE /api/v1/query-history/{historyId}：删除可见历史

无请求体，响应data：

无需登录，正常响应含`"status":"UP"`，可能同时含liveness/readiness分组。

### 7.1 空查询计划问题的修复说明（2026-08-27）

原始问句在旧服务上复现了“DeepSeek返回了空的查询计划”。旧适配器未显式指定思考模式，输出上限固定为1800，且只读取`message.content`，未区分截断、仅思考内容、空回复与响应结构异常。旧日志未保存结束原因，因此不能反推当次失败的具体token分配。

修复后默认显式关闭思考，增加可配置输出上限和最多一次重试；检测到截断时，即使返回文本恰好可解析为JSON也不执行。日志只记录结束原因、正文/思考字符数、token用量、次数和耗时，不记录密钥、用户问题、SQL或模型思考正文。真实API验证的渠道与趋势两条查询均一次成功，最终内容分别使用284和259个输出token，思考字符数均为0；这些是本次样本结果，不作为固定时延或用量承诺。
